# The hiding service without root

## Goal

The hiding service runs as root today. It writes a udev rule per pad into `/run/udev/rules.d`, has udev reload, re-binds the pad's driver through sysfs, and opens nodes it has set to mode 0000. Being able to write udev rules is root whatever else the unit denies, since a rule can `RUN` any program as root; and the unit leaves all of `/run` writable besides. The workspace review ([review.md](review.md), "The hiding service without root") found that, and found two high-severity gaps in how the service decides what a descriptor names (H-1, H-2) and several ways any local user can stop it serving (H-3 to H-6).

This plan makes the service an unprivileged process: a dedicated user with no capabilities, whose whole power is the files a static, shipped udev rule gives its group. It fixes H-1 and H-2 in that shape, as the review decided, and the medium and low findings with them, so none is fixed twice.

## Decisions

Made by the maintainer on 2026-11-22 (review.md's Decisions), after the spikes in `spikes/hider-rootless/`, which this plan replaced (in the history at `934c482`).

- **The service drops root.** It runs as the user and group `ctrlassist-hider`, with no capabilities at all. A root kept and shrunk was set aside: on systemd 262 three of the hardening settings it would lean on (`ProtectKernelTunables=`, `ProtectControlGroups=`, `ProtectProc=`) silently leave `/run` and `/sys` writable under `ProtectSystem=strict`, and a root with no capabilities still started a unit through systemd's private socket and over the system bus. A dedicated user doesn't need the sandbox to keep its uid from mattering. Both designs, and why, are in [the idea doc](../ideas/hider-rebind-options.md).
- **One static rule, shipped with the package, keyed on marker files** the service creates and deletes, in place of rules written at runtime. udev's `TEST` substitutes before it calls `stat()` (`TK_M_TEST` passes its value through `apply_format_value()` in udev 262), so a line can test for a file named after the device's own attributes; the rule is evaluated at every event, so no reload is needed. The service writes only file names, built from strings it has checked.
- **Hidden nodes belong to the service's group,** `GROUP="ctrlassist-hider"`, `MODE="0660"`, with the seat-access tag removed. A group needs no capability where mode 0000 needed `CAP_DAC_OVERRIDE`. The spike showed a seat user who is also in `input` can't open them, and that no ACL comes back through a VT or a user switch.
- **A pad's driver is re-bound by asking udev, a pad at a time.** The service writes a synthetic event, `change <uuid> CTRLASSIST=rebind`, to the `uevent` file of the pad's HID device or USB interface; a shipped rule makes that file writable by the group for devices already known to be pads, and another does the unbind and the probe when it sees the event. The service can then touch nothing but pads, and needs no list of drivers. The other way that worked, driver files given to the group for a listed set of drivers, reaches every device such a driver has, keyboards among them; it is kept in [the idea doc](../ideas/hider-rebind-options.md).
- **The oldest supported distribution may move up** if this needs it. It doesn't, as far as is known: see [Minimum versions](#minimum-versions).

## Design

### The user, the group and the directory

- **The user and its group** come from a `sysusers.d` file in the packages (`u ctrlassist-hider - "CtrlAssist hiding service" - -`), which the deb, rpm and Arch packages have `systemd-sysusers` apply at install, and from `users.users` and `users.groups` in the NixOS module. The user has no home and no shell. It is created whether or not hiding is turned on, since the rule names the group.
- **The marker directory is `/run/ctrlassist/hide`,** the unit's `RuntimeDirectory=` with `RuntimeDirectoryPreserve=yes` and mode 0700, owned by the service's user. A plain `RuntimeDirectory=` is deleted when the service stops, which would lose what a crash left hidden; preserved, it lasts until the unit's own `ExecStopPost=` puts everything back, and `/run` being emptied at boot bounds the worst case. udevd, as root, reads it whatever its mode.
- **The markers are the only record.** Today's `/run/ctrlassist/hidden` records go: a marker is created before the re-bind that makes it take effect, so whatever a crash leaves hidden is named by a marker, and undoing it needs nothing else (see [Reconcile and the sweep](#reconcile-and-the-sweep)).

### The static rule

`72-ctrlassist-hide.rules`, at 72 for the reason today's runtime rules are: after `70-uaccess.rules`, which tags pads for seat access, and after any `60-*` rule that opens hidraw (Steam's sets `MODE="0660"` and the tag), and before `73-seat-late.rules`, which grants what the tag asks for. It does four things, all from the spike's rule text that worked, with the changes below:

1. **The re-bind request.** On a `change` event of a device in the `hid` or `usb` subsystem whose `SYNTH_ARG_CTRLASSIST` is `rebind`: `ATTR{driver/unbind}="%k", ATTR{subsystem/drivers_probe}="%k"`. The probe, not a bind to the same driver, so whichever driver the kernel would pick at a plug-in takes the pad again.
2. **Which devices may be asked.** On the event node of a pad (`ID_INPUT_JOYSTICK` and none of the keyboard, key, mouse, touchpad or tablet classes, as the service's own check), the `uevent` file of its HID device, or, with none, of its USB interface, is given to the group and made group-writable (`chgrp` and `chmod g+w`, run by udev). sysfs keeps a file's owner and mode as long as the device exists, and a HID device or USB interface outlives the re-bind of its driver.
3. **The raw request's nodes.** `DRIVERS=="playstation"` hidraw nodes get `GROUP="ctrlassist-hider", MODE="0660"`, beside whatever seat access they have. A stock hidraw node is root's alone, so this opens nothing to the seat user; the service needs it to open an unhidden DualSense's raw node without root.
4. **Hiding by markers.** Every node of a pad that has a marker (its event, js and hidraw nodes, and the event and mouse nodes of its touchpad and motion sensors) gets `OWNER:="root", GROUP:="ctrlassist-hider", MODE:="0660", TAG-="uaccess"`. The final assignments (`:=`) are a change from the spike, so that a later rule can't open a hidden node again (H-8). A node that isn't a joystick's is hidden only under a device whose `uevent` file the rule has given the group, which it tells by the file's group-write bit (`TEST{0020}`), and never one udev classes as a keyboard or a pointer.

`IMPORT{parent}` has a line of its own wherever an imported value is matched, since udev compares a line's `ENV` keys before it runs the line's import (H-15). Paths in `RUN` are `/usr/bin/chgrp` and `/usr/bin/chmod` in the packages, rewritten to the store's in the Nix package.

### Which pads, and how each is named

A marker is a file directly in the marker directory, whose name says how the rule finds the pad. Every name has a prefix, so an attribute that is empty names a file that doesn't exist; the rule tests no value that carries `/`, so nothing outside the directory is ever looked at; and a match only changes the group of the matching device's own nodes. The service writes, for each pad it hides, every marker below that applies:

| Marker | Written when | Matches |
|---|---|---|
| `addr-<uniq>` | the input device's `uniq` is an address (`aa:bb:cc:dd:ee:ff`, lowercase) | event, js and mouse nodes, through `ATTRS{uniq}` |
| `serial-<vendor>-<product>-<serial>` | no address, and udev gives a USB serial number | event, js and mouse nodes, through `ID_SERIAL_SHORT` |
| `hid-<HID device>` | the pad has a HID device | all its nodes, through the HID device's kernel name (`%b` after `SUBSYSTEMS=="hid"`) |
| `uniq-<HID_ID>-<HID_UNIQ>` | the HID device's own `HID_UNIQ` is set and well-formed | hidraw nodes, through `IMPORT{parent}` |
| `port-<USB interface>` | on USB, with no address and no serial | event, js and mouse nodes under a USB interface of that kernel name (`%b` after `SUBSYSTEMS=="usb", KERNELS=="?*:?*"`), such as `1-2:1.0` |
| `raw-<USB interface>-<HID_ID>` | the pad's HID device sits directly on a USB interface, whatever else it has (not one on Bluetooth through the kernel's HIDP, under the adapter's interface) | hidraw nodes under a USB interface of that name whose HID device is on the USB bus and of that vendor and product |

What this means for each kind of pad:

- **An address** (a DualSense or DualShock 4 on USB or Bluetooth; anything on Bluetooth) names the pad wherever it reconnects. Its event and js nodes are matched by it.
- **A HID pad's hidraw node is matched by its HID device,** not by an address. The HID device keeps its kernel name through a re-bind of its driver, so the node the re-bind makes is hidden whatever the pad's address is doing. This is the fix for review.md's two hidraw notes: a HID pad on USB has no address in its HID device's properties, so its hidraw line went by model and hid every pad of that model; and a real DualSense on USB has its hidraw node made before the driver sets the address, so a line keyed on the address could miss it. Neither matters to a marker keyed on the HID device. On Bluetooth the HID device carries the address from its creation, through the kernel's HIDP or BlueZ's uhid alike, so `uniq-` covers the hidraw node of a pad that reconnects; no `raw-` marker is written for it, the USB interface above a HIDP pad being the adapter's. On USB, `raw-` covers one that reconnects to the same port, written whether or not the HID device has an address by the time the service looks, since a DualSense's driver sets it only after the hidraw node is made. **One that reconnects to another port has its hidraw node open to whatever opens hidraw for the seat user (Steam's rules) until it is shown again:** the HID device is new, its address isn't in its properties, and its port is another. Closing that needs a re-bind as it is opened again, which the daemon would have to expect (see [What the daemon needs](#what-the-daemon-needs)).
- **A serial number** names a USB pad with no address (an Xbox pad under `xpad`) wherever it reconnects. Clones that share a serial share its fate while one is hidden, as they do today.
- **A pad with neither** is named by its HID device and its port, so it is hidden through the re-bind and through a reconnect to the same port. Today's model-only rule, which hid every pad of the model on every seat at its next event, is gone (H-8).
- **A pad with none of these** (no HID device and no usable `phys`) isn't hidden: the service refuses it as unsupported and the daemon grabs it.

A marker that matches another device than the one it was made for (a forged twin with the pad's address, clones with one serial, a pad plugged into the hidden pad's port while it is away) hides that device's nodes at their next event. The sweep below shows them again once no marker names them.

### Asking udev to re-bind

- **Hiding** creates the pad's markers, then writes the request to the `uevent` file of the pad's HID device or USB interface, the device recorded when the pad was checked. The re-bind removes the pad's nodes, which cuts off whoever had them open, and the nodes it makes again are hidden by the rule as they are created.
- **Showing a pad again** deletes the markers no other hidden pad uses, then sends the same request.
- **What replaces `udevadm settle` and the reload.** There is no reload: the rule never changes. In place of settle, the service watches udev's monitor (`AF_NETLINK`, which an unprivileged process may read) from before it writes the request, and waits on state, with every event, and the monitor's socket overrunning, only its cue to read sysfs and udev's record again. The re-bind is done once udev has answered the request, the `change` event carrying its own UUID having come through the monitor, the inputs the device had are gone, a driver is bound, and udev has finished with every node under it since the request (`USEC_INITIALIZED` later, no `ID_PROCESSING`); for a hide, once every node is hidden too, with no ACL entry beyond its mode, and the pad's joystick node is there. Before the answer, what state says may be an earlier re-bind's doing. It fails at once where the rule's effect is missing: the group can't write the `uevent` file; the answer has come and the old inputs are still there, or no driver is bound; or a node came back not hidden. A failure seen with the pad gone, whichever read saw it go, is its unplugging. After the monitor's socket overran, the answer may have been lost, and only then may state alone say done: by udev's order (below), nodes it finished since the request are this re-bind's, unless the kernel removed and made the pad's inputs again between the service reading them and writing the request (an earlier re-bind run just then, a driver making its inputs anew, someone else re-binding the pad), which would be taken for it. No time limit: the wait ends on state and the answer, on the pad being unplugged, or on the client that asked hanging up, whole or its sending alone (see [A hide given up](#a-hide-given-up)); anything else it sends meanwhile, an empty message among it, is left queued, and read in its turn after the wait. Showing a pad again after its client has gone ends on the first two. A wait that ends before the answer leaves the request in udev's queue, and the device's next re-bind runs after it.
- **udev runs a device's re-binds one after another.** It starts an event only once every earlier event of the same device, its parents and its children has run, and answers it once its rules have run, so a later request's answer comes after every earlier request of the device has run, whoever asked (the showing again of a hide given up before udev took it, a hide soon after a showing again whose client hung up, the sweep's); and the nodes an earlier re-bind makes, the device's children, are finished only after the later request has run. The service takes no turns of its own.
- **The wait holds no lock** over the service's other connections; a pad being hidden is marked pending, and a second hide of it is refused as busy.

### Pads with no driver to re-bind

A pad whose event node has no HID device and no USB interface with a driver (a uinput pad another program made) can't be cut off from whoever has it open, and today's way of hiding it, a change event and the nodes' modes put back by hand, needs `CAP_FOWNER` and `CAP_CHOWN`. **The service refuses it as unsupported,** and the daemon, which grabs any pad the service refuses, grabs it. A grab silences readers that already had it open, which hiding by a change event didn't do. That is today's daemon behavior on a refusal, so no daemon change is needed. The daemon's `hidden` flag for such a pad becomes false, which is true: it is grabbed.

### The raw request

`raw` names an unhidden pad by its event node, as today, and is now checked as `hide` is (below). The service opens the hidraw node **of the HID device of the pad presented**, not of the first pad with the same identity (H-2), and only for the PlayStation driver, as today. It can open it because of the rule's raw-node line. `raw of` opens the hidraw node of the HID device a hidden pad has now.

### Checking a descriptor, and finding the pad again

- **A descriptor proves access only if it was opened for reading.** The service checks it with no call that could block on another process's file system: `fcntl(F_GETFL)` must show no `O_PATH` and a readable access mode; `statx` with `AT_STATX_DONT_SYNC` (which a FUSE file answers from its cache) must show a character device of the input major; and `EVIOCGVERSION` must succeed on it, which an `O_PATH` descriptor can't do. Then, as today, udev must classify it as a joystick and nothing a keystroke or pointer could come from, tagged for seat access; and no other input of its HID device or USB interface may be a keyboard or a pointer, which the re-bind would cut off too and the rule can't see from the pad's node. (H-1)
- **The pad's seat must be one where the caller's session is in front:** its `ID_SEAT`, `seat0` when unset, against the seats the login library says the caller is in front on. (H-1)
- **The service acts on the device it checked.** It records the HID device's or USB interface's sysfs path and the input device's, and the re-bind, the opening of the new event node, `raw of`, `reopen` and showing the pad again all act on that path: the new event node is the joystick event node under the recorded device, the same one by order if it has several. Nothing is found again by vendor, product and address while the recorded device exists. The device is recorded as one enumeration of it: a USB interface's place in sysfs is its port's, so for a device on USB the USB device's `USEC_INITIALIZED` is recorded with it, the time udev first finished with it, which udev keeps through every later event of that device and stamps afresh at each enumeration; a device at the same place with another stamp is another pad in the same port, and the recorded one is gone. A HID device needs nothing more, its name ending in an instance number the kernel never hands out twice, but is stamped too when it is on USB. A node opened by its path is checked once open: its device number must name a device under the recorded one, the recorded enumeration still there, and a hidden pad's node must be hidden, its ACL, read on the descriptor opened, with no entry beyond the mode's. (H-2)
- **A pad that reconnected is found again only once its recorded device is gone,** and then only among event nodes the rule has hidden, that are joysticks, on the same bus, with the same vendor and product and seat, under the same kind of device (`/sys/devices/virtual` or not, which a uhid device can't choose), that one of the entry's markers names, and that no other hidden pad has. What is left: a pad that is itself a uhid device (on Bluetooth, through BlueZ) has a twin indistinguishable in sysfs, so a twin a seat user makes while the pad is away can be taken for it on its return. Only the user at seat0 can open `/dev/uhid` (the packaged rule gives it to the seat's user), so this is the seat user's own process against their own daemon, which the service doesn't defend against.

### Who is served, and when

- **A connection is permitted** once its user is found in front on a seat, as today, and stays so. A permitted connection may always restore, say the version, and `reopen` and `raw of` what it has hidden: a user who leaves the foreground keeps what they have, as the architecture says. But a `reopen` that has to find a pad again, its recorded device gone, needs the caller in front now on the pad's seat: what it finds may be a pad someone else plugged in.
- **`hide` and `raw` need the caller in front now,** on the pad's seat. A user switched away from can take nothing new. (H-3)

### Connections

- **One thread per connection,** each receiving, checking and replying for its own client, with the shared state (the hidden pads, the markers) behind one lock that no thread holds while it waits on a client or on udev. A client that never reads its replies blocks only its own thread at `sendmsg`; one that passes a descriptor whose last close blocks (a FUSE file's flush, a lingering TCP socket) blocks only its own thread, since every descriptor received is closed there, the checked ones included. (H-4, H-5)
- **Unpermitted clients are still answered,** so a daemon that started before its session was in front keeps its connection and is served once it is, as today; it costs them only their own thread.
- **At most 40 connections for a user with a session on a seat, eight for any other user, and 32 between all the others.** A connection over a cap is accepted and closed at once. The daemon holds one for each pad it has hidden and one for each request under way beside them, two for each pad and two more at most: 34 for sixteen pads. A user can connect as many user IDs, the subordinate ones a user namespace maps, but logs in at a seat only as their own, so the shared cap leaves room for the users at seats. The unit sets `LimitNOFILE=8192`, room at six descriptors a connection for some thirty users at seats with their caps full. What no cap reaches is the backlog of connections not yet accepted, which is everyone's, the service learning who connects only as it accepts: a user connecting without pause can keep it near full, and a client that connects without waiting is then refused at once. Over-cap connections are closed as they are accepted, with no thread made and nothing read, by one thread kept for closing them and never by the main thread: a client can send descriptors before it is accepted, and their release on the closing thread can block, as a lingering TCP socket's does. With that thread's queue of 64 full, the main thread accepts nothing more until there is room. (H-6)
- **A connection that closes shows its pads again each on a thread of its own,** so that one whose re-bind never ends holds none of the others; the connection's thread waits for them all, and none holds the lock as it waits.
- **`accept` failing is not fatal.** Out of descriptors or memory, the service stops accepting until a connection closes, instead of exiting and showing every hidden pad mid-session. With none open there is no such event to wait for, and nothing hidden, so it stops and says why; systemd starts it again for the client still waiting. A failed `poll` waits on the one thing that matters, blocking: a read of the closings, or an accept on the listener made blocking for that accept alone, since systemd hands it over non-blocking. (H-6)
- **Started on demand, it exits when the last connection closes,** as today; the main thread decides, so a client waiting to be accepted is accepted rather than dropped. How often it starts is then anyone's doing, so the socket unit sets `TriggerLimitIntervalSec=0`, as the service's sets `StartLimitIntervalSec=0`: past the default trigger limit the socket fails and stops listening for everyone.

### Reconcile and the sweep

- **Reconcile,** when the service starts and from the unit's `ExecStopPost=` however it stopped, deletes every marker, then shows again every pad the rule has hidden.
- **The sweep:** a pad is hidden by the rule exactly when its event node belongs to the service's group, which nothing else sets. A raw node can be hidden with its pad's event node not (one of the model of a pad hidden, with another address or serial, plugged into its port while it was away), and its group can't say so, a PlayStation pad's raw node having the group hidden or not; so the rule sets `CTRLASSIST_HIDDEN=1` on every node it hides, which udev keeps in its record of the node until its next event. After a pad is shown again, and at reconcile, the service sends the re-bind request for the HID device or USB interface of each such pad and raw node that no hidden pad's record holds and no remaining marker names. That is how a forged twin, a clone or a pad plugged into a hidden pad's port comes back: the re-bind makes its nodes afresh as the stock rules make them. The sweep writes the requests and waits for none of them, in the running service as in reconcile; the running service holds its state as it does, so a hide of one of those devices is either in the state, and the device left alone, or asks its own re-bind after the sweep's, which udev runs after it. A device with a keyboard or a pointer among its inputs, as a hide refuses, is left as it is, and logged: a joystick node of it hidden by a marker made for another pad stays hidden until it is plugged in again. The raw node's own `uevent` file is root's, so a change event of its own isn't the service's to send; a HID device of a pad's model, which is all a `raw-` marker names, has had its `uevent` file given to the group as a pad's.

### The unit's sandbox

`User=` and `Group=ctrlassist-hider`; `CapabilityBoundingSet=` and `AmbientCapabilities=` empty; `NoNewPrivileges=yes`; `ProtectSystem=strict` with the marker directory the only writable path under `/run`; `/sys/devices`, where the `uevent` files are, the only one under `/sys` (`ProtectKernelTunables=yes` makes `/sys` read-only, and the spike's `BindReadOnlyPaths=/sys` keeps it so on systemd 262, where that setting alone doesn't); `DevicePolicy=closed` with `DeviceAllow=char-input rw` and `char-hidraw rw`; `RestrictAddressFamilies=AF_NETLINK`, since the service creates no socket but udev's monitor (its listener comes from systemd, connections from `accept`); `ProtectProc=invisible`, `ProcSubset=pid`, `PrivateIPC=yes`, `RemoveIPC=yes`, `UMask=0077`; and the packaged unit's other settings. Each is checked in the VM by the service still hiding and restoring. The network namespace stays shared: udev's events arrive over netlink in the host's. `ReadWritePaths=/run` goes. These are defense in depth now: the user's permissions are the boundary.

### What a compromise yields

Not root. The service's user can open the nodes of pads that are hidden and the raw nodes of PlayStation pads, hidden or not, which means reading their input and writing them output and feature reports; have udev re-bind the driver of any pad, and send any pad's HID device or USB interface any synthetic event, which udev processes as root through the stock rules: denial of service on pads, and on a keyboard or a pointer only where one shares a pad's HID device or USB interface, which the rule can't see from the pad's node and the service refuses to re-bind, but never hiding or opening one; and hide any pad by writing markers. It can write nothing outside its own directory and the pads' `uevent` files, and has no capability to lose.

### Minimum versions

What is used: `TEST` with substitution, `IMPORT{parent}`, `TAG-=`, final `:=` assignments, `%b` in `RUN` formatted when its line is applied (udev since its rules engine was rewritten in 243); `CURRENT_TAGS` (247), which the seat-switch behavior the spike observed relies on; synthetic uevent arguments (Linux 4.13); `ProtectProc=` and `ProcSubset=` (systemd 247), `PrivateIPC=` (248), `RuntimeDirectoryPreserve=` (235), `sysusers.d` (215). So **systemd 248 and Linux 4.13**: Debian 12 (252), Ubuntu 22.04 (249), Fedora and Arch are all above it. Only 262 is run in the VM; the rest is from the versions each feature arrived in, not tried.

## The findings, one by one

- **H-1 (an `O_PATH` descriptor names any pad; the seat isn't checked): closed** by the descriptor checks and the seat check above. Shown in the VM by an `O_PATH` descriptor refused for `hide` and `raw`.
- **H-2 (a pad found again by forgeable identity): closed** by acting on the recorded device, and re-identifying only after it is gone, under the conditions above, with the uhid-on-Bluetooth residual stated. Shown in the VM by a uhid twin with another pad's vendor, product and address: hiding the twin returns the twin's node and leaves the real pad visible, and the real pad can still be hidden.
- **H-3 (powers kept after leaving the foreground): closed** for new requests: `hide` and `raw` need the caller in front now. Keeping what was hidden, and `reopen` and `raw of` of it, stay, by the architecture's own promise.
- **H-4 (hanging the service by not reading replies): closed** by a thread per connection. Shown in the VM by a client that sends a thousand requests and never reads, while another is served.
- **H-5 (a descriptor whose close blocks): closed** by closing descriptors on the client's own thread and checking them without calls that wait on another file system. Not shown with a FUSE file in the VM; the thread structure is what H-4's test shows.
- **H-6 (exhausting descriptors makes it exit): closed** by the per-user cap and `accept` failures not being fatal. Shown in the VM by many idle connections from one user while another user's client is served.
- **H-7 (the uinput and uhid grant): not closed here.** It is the daemon's access, not the service's; closing it means the daemon receiving those descriptors through the service, a protocol and daemon change and the service's user needing uinput and uhid. The maintainer's to decide.
- **H-8 (hiding undone by later rules; model rules spill over): closed** by final assignments and per-pad markers, with the spill-over that remains (twins, a pad in a hidden pad's port) undone by the sweep.
- **H-9 (65,535 HID devices): closed.** A HID device's name is checked as the kernel forms it, with four or more instance digits, and it is no longer written to a driver file: the rule uses `%k`.
- **H-10 (sockets leak into `udevadm` children): no longer applies,** the service running no programs; and closed anyway: the listener is made close-on-exec, and connections are accepted with `SOCK_CLOEXEC`. The activation variables are left set, there being no program to inherit them.
- **H-11 (the unit doesn't contain a compromise): no longer applies** in its root form; the sandbox above is added as defense in depth.
- **H-12 (`--listen` sets the mode by path): closed** by binding under a umask that gives the mode, with no `chmod` after.
- **H-13 (truncated requests accepted): closed:** a message longer than a request is refused.
- **H-14 (tokens wrap): closed:** a token in use is never handed out again; and a token no longer names a file.

## The wire protocol

Unchanged by the move off root: the same requests, replies, refusals and sizes, so the daemon of then worked against the new service. Two things the client library changes, neither visible on the wire: `receive` reports a message's whole length, so a reply longer than a reply is a protocol error rather than its first six bytes; and `Refusal::Unsupported`'s text no longer speaks only of raw nodes, being also the answer for a pad with no driver to re-bind.

The second review's fixes left the wire as it was too, and `dislodged` as below; what changed is when some refusals come. `hide` is refused as `Unsupported` for a pad that shares its device with a keyboard or a pointer, and as `Failed`, at once and with nothing marked, where the group can't write the device's `uevent` file; as `Failed` after the re-bind where udev took the request in without re-binding, no driver took the pad again, or a node came back not hidden (where before the first waited for good and the last succeeded); a driver that makes its pad's node only after its probe is now waited for, where before it was refused; and as `Absent` if the pad is unplugged as it is re-bound. `reopen` is refused as `NotPermitted` where it would have to find the pad again and the caller isn't in front on its seat, and as `Failed` where the node it finds isn't hidden. Any refusal of `hide` the daemon already answers by grabbing the pad.

**`dislodged` keeps its meaning:** on a hide, that the service re-bound the pad's driver, and will re-bind it again to show it. Every hide that succeeds now re-binds, so it is always true; a pad that couldn't be re-bound is refused instead. `reopen` still replies `dislodged`, as today, and the daemon still ignores it there.

### A hide given up

The daemon hides each pad on a connection of its own, and gives a hide up by hanging that connection up, whole or its sending alone; the service, seeing the hang-up in its wait for the re-bind, stops waiting, refuses the hide as `failed`, shows again what the connection hid, by a second re-bind if the first was asked, and then closes its end. Anything else a client sends during a hide, an empty message among it, stays queued, and is read in its turn after the hide. What the pad goes through meanwhile is the daemon's book's to see, by the pad's anchor ([rebind-by-identity.md](rebind-by-identity.md)), not the service's to say.

For a while it was said: the second review's follow-up added a `cancel` request, a refusal `cancelled`, a count of the re-binds each request made in every reply, and a mark in the reply to `version` saying the service took `cancel` and counted, so that the daemon's count of a pad's goings and comings back would be exact. [rebind-by-identity.md](rebind-by-identity.md) took all of it out again, as the Deviations say.

**The wire as it is:** fixed-size, and each message checked whole.

- **A request is five bytes:** an opcode, then a token, a 32-bit little-endian number. Opcodes: 1 `hide`, 2 `reopen`, 3 `restore`, 4 `raw`, 5 `raw of`, 6 `version`. A `hide` and a `raw` carry one descriptor beside them; the others none, and their token is 0 where they name no pad.
- **A reply is six bytes:** a status, the token, and a flags byte. Status 0 is done; a refusal is 1 `not permitted`, 2 `not a pad`, 3 `busy`, 4 `unknown token`, 5 `absent`, 6 `failed`, 7 `bad request`, 8 `unsupported`. Bit 0 of the flags is `dislodged`; no other bit is set, nor read. The token of a reply to `version` is the release, packed. A reply to `hide`, `reopen`, `raw` and `raw of` that did as asked carries one descriptor beside it.
- **Anything else is no message:** the service refuses a message of another length or with an opcode it doesn't know as `bad request`, but for an empty one, which it reads as the connection's end, and the client takes a reply of another length or with a status it doesn't know for a broken protocol. The numbers left by `cancel` (opcode 7) and `cancelled` (status 9) were the last of each, so none is skipped.

### What the daemon needs

Nothing for this plan. For the one case left open (a USB HID pad that reconnects to another port while hidden), the service could re-bind it as it is opened again, if the daemon then expected the pad to go and come back once more, as it does when it lets a pad go. That needs `reopen`'s `dislodged` to mean "re-bound now" and the daemon to act on it, and is not done here.
