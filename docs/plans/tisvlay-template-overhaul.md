## Goal

Rewrite CtrlAssist from a clean slate, using [TisVlay](https://github.com/TisVlay/TisVlay) as the reference for project style, architecture and patterns, and move the repository to the `CtrlAssist` GitHub org.

The legacy code (0.4.0: one crate, 3,900 lines of Rust, no tests) is a reference for *what users could do*, not for how it was done and not as a compatibility target. The end state offers similar functionality; the CLI, config file, tray layout, app ID and crate layout are all free to change. We are pre-1.0.

Why a rewrite rather than a migration:

- **The open issues are architectural.** Packaging (#9), a GUI (#7), a config file for advanced multiplexing (#6), latency (#10), splitting one device into several (#53) and faithful PlayStation identity (#5) each want something the legacy shape lacks: a long-lived owner of the devices, a general routing model, a testable core, a release pipeline.
- **Nothing is tested,** so there is no behavior to preserve with confidence. A migration would churn every file twice: once to move it, once to redesign it.
- **A generalization was already tried and stalled** (the `refactor-claud-opus-4.5` branch). See [Lessons from the earlier refactor](#lessons-from-the-earlier-refactor).

This is a program plan. It fixes the decisions, the spikes and their exit criteria; the commit-sized build steps are written at step 4, from the spike findings. That and the other departures from the template's process are listed under [Departures from the template's process](#departures-from-the-templates-process).

## Terms

One word per thing, here and in everything written from this plan:

| Term | Meaning |
|---|---|
| pad | A physical controller. Not "controller" or "device", except in crate names. |
| virtual pad | A controller the daemon creates for games to read. |
| source, sink | A pad, or a virtual pad, as it appears in a graph. Input flows source to sink; feedback originates at a sink and flows to sources. |
| node | A transform between sources and sinks (a mux or demux mode). |
| graph | Sources, nodes, sinks and the edges between them. |
| profile | A saved graph with its settings, in a file the daemon owns. |
| preset | A built-in profile shape a client offers by name (assist, swap, split). |
| setup | A profile that is currently running. |
| hide | Keep games from seeing a pad. A grab is one mechanism for it. |
| identity | The name, IDs and, where emulated, the HID personality a virtual pad presents. "Spoofing" is the legacy word. |
| feedback | Anything flowing from game to pad: force feedback (rumble is one kind), LEDs, trigger effects. |

## Ground rules

1. **Architecture before build.** The crate split, process layout and data flow are designed up front from spike results and written into `docs/architecture.md`. No piecemeal migration.
2. **TisVlay is the template.** Tooling, lint policy, CI shape, docs layout, release flow and code conventions are copied from it and trimmed, not re-derived. Where CtrlAssist departs, the plan says why.
3. **No backward compatibility.** No config migration, no CLI aliases, no shims.
4. **Behavior is specified as tests before the engine exists.** The routing semantics live in a pure crate with no device access, and its tests are the spec.
5. **Input events never cross IPC.** The data path stays in one process; IPC carries control and state only.
6. **Spikes lean into each technology's idioms.** A spike is an independent workspace under `spikes/<name>/` with a README, written the way that technology wants to be used. Where a spike compares candidates, each gets its own artifact; no shared abstraction across them.
7. **Tooling arrives with its first use.** A gate, workflow or document lands in the commit that gives it something to govern, not ahead of it.
8. **One campaign branch,** a commit per slice, each passing the gates that exist. How it is cut into PRs is decided when the shape is final; a history that begins by deleting the legacy tree may well land as one merge.

## Decided

**Repository.** Transfer `ruffsl/CtrlAssist` to `CtrlAssist/CtrlAssist`: issues, stars and LFS objects carry over and old URLs redirect, provided no repository is later created under the old name. The maintainer does this out of band, and no local work waits on it: files are written against the final URLs and app ID from the start, and everything that needs GitHub (CI runs, required checks, environments, trusted publishing, Read the Docs, Codecov) is switched on afterward. The rewrite lands on `main` in the same repo: one commit removes the legacy tree, and `v0.4.0` plus a `legacy/0.4` branch keep it reachable.

**App ID** is `io.github.ctrlassist.CtrlAssist`.

**Packaging channels:** deb, rpm and an Arch package through TisVlay's pipeline unchanged (`cargo auditable zigbuild --profile dist`, `cargo nfpm`, Sigstore attestations, draft GitHub release), and a Nix package with a NixOS module. This covers what #9 asks for apart from a bare binary download and Flathub.

**A user-level daemon,** unlike TisVlay's system daemon: the pads belong to the seat user and Steam's config is in their home. The packages install static udev rules for what the daemon needs (uinput access, and uhid if S5 calls for it).

**Privilege is confined to a minimal helper.** The daemon never runs as root. The hiding spike found no unprivileged way to make a pad absent to games ([architecture](../architecture.md#hiding)), so the native packages install a small root helper that does one thing: on request it installs a runtime udev rule denying a pad's event, js and hidraw nodes to everyone, opens them itself and passes the open descriptors to the daemon, and removes the rule and restores the nodes when the daemon's connection closes, crash included. It hands over descriptors rather than permissions because the daemon and the games are the same user. Hiding is the rule followed by re-binding the pad's driver, which cuts off programs that already had the pad open, as Steam does from plug-in; restoring re-binds again, so they see the pad return. The daemon names a pad to the helper by passing an open descriptor it already holds, never a path or a name: possession proves it could already read that pad, and no attacker-chosen string reaches a rule. The helper refuses anything that isn't a joystick the seat user could open, builds rule text only from parsed numbers, and opens hidraw only for an allowlisted driver. The active seat user may connect to it, enforced on its socket the way TisVlay enforces its own; no prompt. Channels that can't install it, the Flatpak above all, fall back to a grab plus Steam's blacklist, with the gaps the finding lists.

**InputPlumber is out of scope for the first release.** CtrlAssist works independently and documents that the two shouldn't manage the same pad. Cooperation could not be tested on the development host and would be a second, unexercised code path.

**Daemon and thin clients, as separate processes of one binary.** `ctrlassist service daemon` owns the pads and the graph. The CLI, tray, GUI and TUI are clients. Reasons to split rather than run one process: a GUI toolkit shouldn't share a process with the input loop; a client crash shouldn't drop the virtual pad mid-game; a gamescope session may have no tray; and the engine must outlive a settings window.

**Flatpak is a second-tier channel.** It can run the same user-level processes inside its sandbox and gets whatever hiding works there. It matters because SteamOS and Bazzite are immutable, but it is not a first-release gate.

**The core abstraction is a routing graph** of sources, nodes and sinks, with feedback as part of the model from the first test. It unifies mux, demux, the legacy cookbook's chained instances and splitting one pad into several (#53), and it is what a profile describes (#6). Profiles are validated as acyclic.

**Crates.** `ctrlassist` on crates.io becomes the client SDK; the binary lives in `ctrlassist-cli`, as in TisVlay. `cargo install` is no longer a supported install path, because a daemon needs a unit file and udev rules cargo can't install.

**zenoh for the control plane,** as in TisVlay, over a Unix socket in `$XDG_RUNTIME_DIR`. The alternative is the session D-Bus through zbus, which is already in the tree for the tray and would give activation and name ownership for free. zenoh is chosen because TisVlay served D-Bus first and moved off it for type safety and API ergonomics, and because its protocol, SDK and state-watching patterns carry over directly. Performance work belongs to the data path, which never touches it (ground rule 5). S3 checks only that sharing a process with it is harmless.

**Presets first, graphs in profiles.** Clients offer presets; arbitrary graphs can be written in a profile file from the first release; no client edits them visually.

**Disconnects hold and re-bind.** When a pad in a setup drops, the virtual pad stays alive so the game never sees a disconnect, the missing pad's inputs go neutral, the other pad keeps working, and the same pad is re-bound and re-hidden when it returns. A notification says what happened.

**Virtual pads come in two kinds, chosen by identity** ([architecture](../architecture.md#virtual-pads)). A uinput pad serves the generic identity and Xbox identities. A PlayStation identity needs a uhid pad, because SDL and Steam ignore an evdev node carrying Sony's IDs. The default, when a profile names none, is the generic one: a virtual pad that claims to be real hardware is a choice. Copying a pad means its IDs on a uinput pad for Xbox-family pads and a uhid copy for PlayStation pads.

**The DualSense identity and the Steam blacklist fallback are in the first release, built last.** Everything else is brought up end to end with generic and Xbox identities and the helper first, so either can slip to a point release without holding 0.5.0. Two reviewers recommended deferring both; the maintainer chose to keep them.

**A DualSense identity is copied from a connected pad, never shipped.** Its report descriptor and feature reports are read from a real DualSense and cached per pad in the user's state directory, so the identity is offered only to someone who has had one connected, and nothing of Sony's is carried in the repository. *Reversed on 2026-11-21: the descriptor ships and a copied pad overrides it; see "For review".*

**Feedback routes rumble everywhere and passes the rest through between like pads.** Rumble is translated between the two forms (force-feedback requests on uinput, output reports on uhid). When the sink and the source are the same kind of pad, the whole output report passes through, so LEDs and trigger effects work; between unlike pads they are dropped.

**Pads are read directly through evdev, on one epoll thread** ([architecture](../architecture.md#the-input-path)). gilrs leaves the dependency set: it opens pads by path, so it can't take the descriptors the helper hands over, and its loop wakes about a hundred times a second when idle where the new one never does. The first release includes its own parser for SDL's controller database, so pads outside the Xbox and PlayStation families, which gilrs used to normalize, keep working.

**The input thread asks for real-time scheduling and degrades quietly.** If the kernel refuses, the daemon runs normally and its status says which. Packages raise the limit where they can; rtkit is not used.

**Activity is split between the source and the node.** A source has a deadzone that zeroes its rest noise before any node sees it, since a worn stick is a fact about the pad. A mux node has an engage threshold and a lower release threshold on what remains, since "is the assist touching this?" is the mode's question and two thresholds stop a hovering stick from flickering between owners. Defaults match the legacy 0.1, so most profiles set neither. No ownership is held by a timer.

**Ownership is over groups, not pairs.** A group is a set of controls owned together: a stick's two axes, a yoke's three, a flight grip's axes with its trigger and hat, a lone button or throttle as a group of one. One rule replaces legacy's separate cases: per group, whoever is active on it owns every member. A gamepad's groups are derived from the well-known control names, so an ordinary profile declares none; a profile may declare or regroup them for other devices.

**A mode is a merge rule per group.** Legacy priority mode already had an exception (triggers aren't owned; the larger value wins), so the routing graph spike models each mux mode as a table of rules over the same machinery (owned, largest, blended, switched) and reports whether that expresses all three without special cases.

**On a switch, the virtual pad takes the incoming pad's state.** What both pads hold stays down with no blip, what only the outgoing pad held goes up, and analog values step to the incoming value. After any switch the sink equals the active source, which is an invariant the tests check.

**A game's rumble upload is answered leniently.** It is told the effect is accepted if any target pad took it, and also when rumble is switched off; it is refused only when every pad asked refused it. A game that insists on rumble then still runs when one pad lacks it.

**A profile names a pad by address or by model.** By address when it must be that exact pad, which is what a client records when a setup is created; by model ("any DualSense") when any will do, which is what makes a profile shareable between machines.

**Pad state holds 64 buttons and 16 axes.** Measured against 128 and 32, which costs about three times as much per step. Raising it later means first changing the step to visit only the positions in use.

**A daemon restart drops its virtual pads, for now.** The game sees a disconnect and the helper restores the hidden pads, so it falls back to the real ones. Keeping virtual pads alive across a restart is an idea, not first-release work.

**Rumble is routed as levels, mirroring the kernel.** The router keeps each game's effects and their timing, computes one strong and one weak level per pad, and keeps a single effect on each pad updated to it, as the kernel's own layer for rumble-only pads does. Within one virtual pad, playing effects add and clamp; when two virtual pads rumble one pad at once, the strongest request wins on each motor. The alternatives and the prior art are kept in [ideas/rumble-routing-model.md](../ideas/rumble-routing-model.md).

**Hiding a pad disconnects it from whatever had it open,** when a setup starts and again when it stops. That is accepted: the real pad vanishes from running games and Steam and the virtual one appears, with nothing restarted.

**The switch is an input to the node, not a pad event it happens to see.** In the first release it can be raised by one button named in the profile (default Mode, consumed rather than forwarded), on whichever source the profile names, or by a client through a daemon rpc. Modeling it as a signal means later triggers don't change the node.

**The legacy words stay, for users too:** primary and assist for the roles; mux with priority, average and toggle; demux with unicast and multicast. Two alternative families were tried and read worse: these are precise, already paired, already in the README and issues, and "assist" is the project's name. Clients add a one-line description beside each, since the mode names are jargon to a newcomer.

**Setups start manually, with optional auto-start.** A client starts a setup. A profile may also be marked to start by itself once the daemon is up and all of its pads are connected.

**Clients are built in the order CLI, tray, GUI, TUI.** The GUI is Slint, following TisVlay. The TUI uses ratatui and comes last because TisVlay has none to pattern it on; the `archive/feature/tui` tag holds an earlier draft worth reading first. Each can mirror live pad state, which the daemon publishes on change and only while something subscribes.

**The first release is daemon, CLI and tray,** matching the surfaces 0.4.0 has (a CLI and a tray). The GUI and TUI follow as later minor releases. It is verified on NixOS with KDE, the maintainer's host; the deb, rpm and Arch packages are built and container-tested but not hardware-verified.

**The event model isn't gamepad-shaped, but only gamepads are built.** See [Event model scope](#event-model-scope).

## Constraints the design must respect

Facts about the platform that the plan review surfaced. The spikes test the ones in doubt; the architecture must answer all of them.

- **Hidden means absent, not silent.** A grabbed evdev node still enumerates, so a game may list a dead pad and give it player 1, and hidraw has no grab at all. Hiding is judged by whether the consumer still lists the pad.
- **Hiding must survive a crash.** Legacy restored permissions and Steam's config on `Drop`, which a kill or power loss skips, leaving pads hidden. Prefer mechanisms the kernel undoes when the process exits. Any persistent change is recorded before it is made, reconciled when the daemon starts, and undone when its unit stops.
- **Force feedback is a blocking request protocol.** A game's effect upload blocks until the daemon answers, so a stalled input thread stalls the game. Effect slots are limited and per pad, effect IDs are per pad, a target may reject an upload, effects die with the handle that uploaded them, and gain and autocenter arrive separately. Fan-out to several pads needs a policy for what the game is told on partial failure; a demux creates fan-in, several games driving one pad. Legacy also let rumble go to a pad other than the one providing input, so feedback routing is not simply the input edges reversed.
- **A virtual pad's capabilities and identity are fixed at creation.** Changing them means destroying and recreating it, which the game sees as a disconnect. So a sink is created from what the profile declares, with a copied identity cached by hardware ID rather than read from a pad that may be absent. Changes to a running setup are either live (the sink is untouched) or disruptive, and clients say which.
- **Merging different pads needs a common layout.** Raw evdev layouts differ between drivers (which axis is the right stick, hats against d-pad buttons, analog against digital triggers, ranges), and a sink that copies a real pad's IDs gets that pad's mapping applied by SDL, so its layout must match. Events are processed in whole report frames, and a dropped-events marker forces a resync.
- **The daemon must not consume its own output.** Its virtual pads are excluded as sources by a marker. Other software's virtual pads (Steam Input's, InputPlumber's) are opt-in, since on a handheld one of them may be the only usable source and Steam's may itself wrap a CtrlAssist sink.
- **The development host masks permission questions.** Its `/dev/uinput` and `/dev/uhid` are accessible only because Steam's and Sunshine's udev rules are installed. Permission findings come from a clean NixOS VM.

## Event model scope

The core model carries gamepads, wheels and HOTAS, and gyro, touchpad and LEDs. All are designed for; only gamepads are built.

- **Controls are open-ended.** A control is identified by kind and index, with the standard gamepad buttons and axes as well-known names over that space rather than a closed enum. A HOTAS with 30 buttons and 8 axes is representable without a vocabulary change. The mux nodes need generic control addressing anyway to route per control (#53). Well-known names are what make two different pads mergeable; controls outside them pass through unmerged.
- **Feedback kinds are open** (a force-feedback effect, a device's output report), so a wheel's constant-force and spring effects pass through even though only rumble is tested.
- **Motion and touch kinds are reserved.** A uhid sink could carry them; nothing in the first release produces them.

Deferred: implementation and verification on wheel or HOTAS hardware, which isn't on hand. If S4 shows the open-ended form costs more than this, its finding says so and the decision is revisited.

## Lessons from the earlier refactor

The `refactor-claud-opus-4.5` branch defined `CtrlEvent`, `EdgeState`, a `Node` trait with ports, and a `GraphExecutor`, with ten unit tests over the core. Its mid-course assessment found the executor built but bypassed by hand-wired code; by the branch's end `mux2` does run input through the executor, but force feedback is still a separate thread outside the graph, a "hybrid" by its own description. Toggle mode sent rumble to both pads until a test pinned it.

The maintainer's account of why it stalled: nothing compared the new path's behavior with the legacy one, so features couldn't be ported without risking silent regressions.

What this plan takes from it:

- The event vocabulary (normalized axes, named buttons, forward input and reverse feedback) is the starting point for the core crate.
- Feedback is in the graph from the first test, with its request-and-reply shape, not a thread beside it.
- The spec comes first: scenario tests in a pure crate, then nodes, then an executor the tests run through, then devices. The behaviors are curated here rather than inherited.
- The node API is designed for the hot path (the branch's returns a `Vec` per event and holds state as `dyn Any`).

## Feature goals

The rewrite targets similar functionality, not identical.

| Legacy feature | What it did | In the rewrite |
|---|---|---|
| Mux: priority | Assist overrides primary while active: per button, per stick as a pair; triggers take the larger value | Preset |
| Mux: average | Blend both pads' axes, OR the buttons | Preset |
| Mux: toggle | Assist's Mode button switches the active pad, with a resync | Preset; the switch binding becomes configurable |
| Demux: unicast | Route one pad to the active one of N virtual pads, cycled by the Mode button, neutralizing the one left | Preset, as a node |
| Demux: multicast | Copy one pad to all N virtual pads | Preset, as a node |
| Chained instances | Shell scripts with `sleep 1` wiring demux outputs into mux inputs | One graph in one daemon, written in a profile |

| Hide: system | chmod device nodes; needs root | Decided after S1; no `sudo ctrlassist` |
| Spoof | Virtual pad copies a pad's name and USB IDs | Identity: copy a pad or pick a built-in one; depth decided after S5 |

## Ecosystem survey

The legacy dependencies were chosen a year ago, and the Rust input ecosystem moves quickly. Before the spikes pick their building blocks, survey it and write a finding:

- **Legacy dependencies** (`gilrs`, `evdev`, `udev`, `ksni`, `notify-rust`, `ashpd`, `fs2`, `dirs`, `signal-hook`, `parking_lot`, `env_logger`, and the common ones TisVlay already pins): the current release, what changed since the pinned version (gilrs's changelog especially), maintenance state, and what TisVlay uses in that role.
- **Alternatives by goal:** evdev and uinput access; hidraw and uhid (the `archive/uhid` tag tried `uhid-virt` and `hidapi`); controller mapping databases; HID report descriptors and ready-made controller emulation, PlayStation above all; hotplug (udev bindings against pure-Rust netlink); epoll-style loops beside tokio; ratatui; graph or dataflow crates worth borrowing from.
- **Prior art:** how InputPlumber, Steam Input and SDL handle hiding, identity and routing, under which licenses, and how handhelds with built-in controllers present them.

Each entry records its source and date. The survey chooses nothing: it gives each spike its candidates. Done when every bullet above has an entry and each spike below has a candidate list.

## Spikes

Each spike is a workspace under `spikes/<name>/`, run on the development host, with the maintainer asked only for physical actions such as pressing buttons, batched into one checklist per session with results captured to a log. On that host the maintainer has allowed: grabbing and releasing pads; editing Steam's config, backed up first and restored after each test; restarting Steam; and `sudo` for temporary udev rules and node permissions, each command shown before it runs and undone afterward. Each ended in a finding holding a results table and a verdict, with a stop for review. The findings were then folded into `docs/architecture.md` (hardware caveats into `docs/concerns/`) and deleted; git history has them. Spike code is deleted in the commit that lands its replacement in `crates/`, except S4, whose tests and nodes are promoted to become the core crate.

Order: the survey, then S1 and S5, then S2, then S4, then S3. S5 precedes S4 because the sink type decides what feedback looks like; S1 precedes S2 because a grab decides who may read the pad.

### S1. Hiding, permissions and identification

*Question:* can an unprivileged daemon make a pad absent to games, and what must the packages install?

- [x] For each mechanism (evdev grab; Steam's blacklist; SDL's ignore-devices hint per launch; node permissions and a runtime udev rule set by root) and each consumer (Steam, read from its controller log; an SDL test tool run natively on both of its backends; raw evdev and joydev readers), record: absent, present but silent, or visible. A Proton game is left to a later check.
- [x] For each mechanism, record what remains after the daemon is killed without cleanup, and after the pad reconnects.
- [x] Record Steam's behavior by start order and whether a change needs a Steam restart.

## For review

Decisions made while building through a marked stop, for the maintainer's QA. Each says what was chosen and what else was on the table.

- **How a pad is named across reconnects** (build step 10). One name per pad, the most specific thing it reports, written as `address:<uniq>`, `serial:<vendor>:<product>:<serial>`, `port:<vendor>:<product>:<phys>` or `model:<vendor>:<product>:<name>`. The order is the architecture's; the written form is new, and profiles will use it. A pad with no address or serial is the same pad only while it stays in its port, and a uinput pad from other software is known by model alone. Alternative: keep the parts as separate profile keys instead of one string. *Reviewed and kept by the maintainer.*
- **Where the controller database comes from** (build step 11, a marked stop). A snapshot of [SDL_GameControllerDB](https://github.com/mdqinc/SDL_GameControllerDB)'s Linux entries (752 at commit `4e87e3c`), committed under `crates/ctrlassist-device/data` with its zlib license and compiled in. A user's file in the same format is laid over it; the daemon will read it from its config directory. Alternatives set aside: fetching at run time (needs the network, and trusts it), or shipping no data.
- **How it is updated** (build step 11). `just update-controller-db` rewrites the snapshot from upstream's default branch and names the commit in the file's header; a person reviews the diff and commits it. Nothing updates it automatically. Alternative: a scheduled workflow that opens a PR. *Reviewed and kept by the maintainer.*
- **Which pads use it** (build step 11). Not pads whose kernel driver is on a list of gamepad drivers (`xpad`, `xpadneo`, `xone-gip-gamepad`, `microsoft`, `playstation`, `sony`, `nintendo`, `hid-steam`, `steam-deck`): those are read as the driver presents them. Any other pad uses its database line if it has one, and is read as a gamepad if not. The list is my reading of which drivers follow the kernel's gamepad convention and has only been exercised for `xpad` and `playstation` on this host. Alternative: trust the database for every pad, as SDL does. *Reviewed and kept by the maintainer, 2026-11-21.*
- **What a database line can say** (build step 11). Buttons, whole and half axes, inverted axes, hats, and the two-buttons-as-one-axis form; the extra buttons (`misc1`, paddles, `touchpad`) take fixed spare positions 15 to 25. SDL's hints (`crc`, `hint`, `sdk`, `type`, `face`) are ignored.
- **The profile format** (build step 12, a marked stop). As the architecture drew it, with these choices made on the way. All are in `crates/ctrlassist-protocol/src/profile.rs` and its fixtures, and are the user-facing format, so they are the ones most worth your eye:
  - *Presets:* `priority`, `average`, `toggle` (keys `primary`, `assist`), `unicast`, `multicast` (keys `pad`, `outputs`, default 2), each with an optional `identity`. A preset can't be mixed with `[source]`, `[node]` or `[sink]` tables; to adjust one, write the full form. Alternative: let a preset take overrides such as `engage`.
  - *Naming a pad:* a bare address, a full name as `ctrlassist pads` will print it, or `model:<vendor>:<product>` in hex for any pad of a model. The architecture's example said `model:dualshock4`; there is no table of model nicknames, so it is numbers for now.
  - *Two pads of one model:* `model:<vendor>:<product>` means any pad of that model, so it can't tell two identical pads apart; an exact name (`address:`, `serial:`, `port:`) can. The maintainer asked about this on 2026-11-21. As built (build step 16): two sources naming the same model each take a different pad, in the order the pads connected; once a source has taken a pad, it waits for that pad and no other if it leaves; and `ctrlassist pads` prints each pad's exact name to paste when the order matters. Alternatives: refuse a profile whose model reference matches more than one pad; or a table of nicknames, which would not solve this either.
  - *Names* of sources, nodes and sinks are lowercase letters, digits and hyphens, and a node may not share a source's name.
  - *Numbering follows name order,* not file order, so in a preset the assist is source 0 and the primary source 1. Nothing a user sees depends on it; state and rpcs will use names.
  - *Feedback* is `"active"`, `"none"`, or for a mux a list of its inputs. *Switch* is a button name, `{ button, input }`, or `false`. Buttons are named `south`, `east`, `north`, `west`, `left-bumper`, `right-bumper`, `select`, `start`, `mode`, `left-thumb`, `right-thumb`, `dpad-up` and so on.
  - *Rules* are overridden per kind of group (`stick`, `trigger`, `button`, `hat`), not per group. Custom groups, for pads that aren't gamepads, have no key yet.
  - *Identity* is `generic` or `xbox`; `playstation` arrives with that identity.
  - *Unknown keys are errors,* so a typo is caught; the cost is that an older daemon refuses a newer profile outright, which the schema version also does.
- **How a pad's key is made** (build step 14). `ctrlassist/pad/<id>` takes 16 hex digits: an FNV-1a hash of the id the pad is known by, which is free text and can't go in a key. A client can compute it, so no lookup is needed. Alternative: a random id minted per pad and stored, as TisVlay mints a UUID per TV, which would survive a pad changing what it reports but needs the store to translate.
- **What `identify` does** (build step 14). The request carries the duration (the CLI's default is 600 ms, `--millis` changes it, and the daemon refuses nothing and more than 5 s); both motors run at about 60%. The daemon opens the pad's event node itself for the buzz; a pad inside a setup is buzzed through the input thread, where the buzz overrides a game's rumble for its duration, as the maintainer chose. The duration is the caller's own, so I did not treat it as a new timeout; say if you read the rule differently. *Reviewed and kept by the maintainer, 2026-11-21.*
- **What is remembered of a pad** (build step 14). `pads.toml` in the state directory, schema 1: id, name, model, and whether it could rumble. Every pad seen is remembered until `forget`, which is refused while the pad is connected. Whether a pad can rumble is asked by opening its event node read-only as it connects. Alternative: remember only pads a profile names. *Reviewed and kept by the maintainer, 2026-11-21.*
- **Two pads that report nothing to tell them apart** (build step 14) share one entry, connected while either is; `identify` buzzes the first. This is the same case as the open question on two pads of one model above.
- **Whether an identity is available** (build step 14) is whether `/dev/uinput` could be opened when the daemon started. It isn't checked again, so installing the udev rule under a running daemon needs a restart to show. Alternative: check on each read, or watch the node. The same holds for looking for the hiding service once at start. *Reviewed and kept by the maintainer.* Changed by the maintainer on 2026-11-21, after a dev daemon that started before the service never copied a DualSense: the hiding service is looked for again each time it is needed until it is found. `/dev/uinput` is still looked at as identities are published.
- **The CLI reads state through the SDK** (build step 14), where TisVlay's CLI subscribes for itself and takes what arrived once no sample has come for 400 ms. The SDK knows when the state is complete from the keys the daemon lists, so `pads` needs no quiet window; that is one duration fewer, and one way to read state instead of two.
- **How a profile is named and kept** (build step 15). Under a name of 1 to 32 lowercase letters, digits and hyphens, the rule sources and nodes already follow; the name is the file's (`<name>.toml`) and the key's, with no separate id. `ctrlassist profile put <file>` takes the file's name unless `--name` is given. The daemon keeps the text as given, comments included, at most 64 KiB. Alternative: a minted id with a free-text display name, as TisVlay's profiles have; it allows renaming without breaking references, and costs a lookup everywhere a person names a profile. *Reviewed and kept by the maintainer, 2026-11-21.*
- **Files changed behind the daemon's back** (build step 15) are read at start only: a file in the profiles directory that is wrong, or written for a later schema, is listed with its problem and left untouched, and an edit made while the daemon runs is not seen until it restarts. The architecture says clients write through the daemon, so nothing watches the directory. Alternative: a `reload` rpc, or watching the directory. *Reviewed and kept by the maintainer, 2026-11-21.*
- **`validate` is an rpc the CLI uses** (build step 15), though the CLI could check a profile itself with the same code. It keeps one answer to "would the daemon take this", at the cost of needing the daemon running to check a file.
- **A setup goes by its profile's name** (build step 16), so a profile runs at most once and `ctrlassist start couch` / `stop couch` need no second name. Alternative: a minted id per run, which would let one profile run twice over different pads. *Reviewed and kept by the maintainer, 2026-11-21.*
- **A setup may start without all its pads** (build step 16): it starts held, with the virtual pads made, and takes each pad as it connects. Auto-start is the one that waits for every pad, as the architecture says. Alternative: refuse to start until every pad is connected. *Reviewed and kept by the maintainer, 2026-11-21.*
- **A start that fails leaves nothing behind** (build step 16); the caller has the reason in the reply. The failed phase is for a setup that was running and stopped working, and that one stays listed, with its reason, until it is stopped. Alternative: list every failed start until it is cleared.
- **A pad a setup uses can't be forgotten** (build step 16), connected or not, and two setups can't share a pad: the second is refused with `pad-in-use`.
- **What happens without the hiding service** (build step 16): each pad is grabbed, which the architecture lists beside Steam's blacklist as the unprivileged fallback; the blacklist half arrives with the PlayStation identity. The daemon looks for the service once, at start, so installing it under a running daemon needs a restart. A pad the service refuses is grabbed and the setup starts anyway, with a warning in the log; the pad's state then says it isn't hidden. Alternative: refuse to start a setup whose pad can't be hidden, so a half-hidden setup can't happen silently.
- **`stop` returns when the pads are back** (build step 16): the reply waits until the virtual pads are gone and the hiding service has restored the pads, not only until the input thread let go.
- **What completes, and its one duration** (build step 17). Pads by id, profiles and setups by name, each with a word about it (a pad's name, a setup's phase), read from the daemon's state through the SDK. A node's name and its choices for `select` don't complete yet. Completion is cut off at 600 ms, TisVlay's ceiling, so a daemon that is reachable but silent can't hold the prompt; with no daemon it returns at once. TisVlay's second duration, the 150 ms quiet window, isn't needed: the SDK knows when state is complete. Completion always asks the default socket, as in TisVlay, because it runs before `--socket` is read. Installing the registration scripts comes with packaging.
- **What the NixOS module does and offers** (build step 22). `services.ctrlassist.enable` puts the package on the path, loads uinput and uhid, installs the udev rule, starts the hiding service's socket, and runs the daemon as a user service wanted by `default.target` and the tray wanted by `graphical-session.target`. Three switches, all on by default: `hiding`, `realtime` and `tray`. The real-time limit is given by setting `LimitRTPRIO=10` on `user@.service`, which raises it for every user's services, not only CtrlAssist's; the daemon's unit asks for the same. Alternatives for the limit: a PAM limits entry, or leaving it to the admin. The tray's unit needs a desktop that reaches `graphical-session.target`. The maintainer asked for research and a spike before deciding (2026-11-21); the finding is in `spikes/realtime/README.md`: the drop-in and a PAM limit both work for a user service on NixOS, and rtkit works only with a CPU-time limit that kills the process on overrun and only for a logged-in user. For the deb, rpm and Arch packages the maintainer chose to ship the same drop-in. *Reviewed after the spike, 2026-11-21: the maintainer keeps the drop-in.* The daemon unit's own `LimitRTPRIO=10` line is removed, as the maintainer chose once the sources showed it can cap but never grant.
- **What the deb, rpm and Arch packages do at install** (build step 23). They enable the daemon and the tray for every user (`systemctl --global enable`), start the hiding service's socket, load uinput and uhid, and install the real-time drop-in, which the maintainer chose. A user who doesn't want the daemon masks it. Alternative: install the units disabled and have each user enable them. The packages depend on libudev and libsystemd by each distribution's name for them, and were installed and tried in containers of Debian 12, Ubuntu 22.04, Fedora and Arch, where systemd isn't running: the units starting is covered only on NixOS. *Reviewed and kept by the maintainer, 2026-11-21.* Since build step 20 the hiding service's unit has no start limit: it exits when its last client goes and is started by the next, and five short-lived clients in ten seconds used to leave it refused, and hiding with it, until someone reset it.
- **What was left out of TisVlay's release machinery** (build step 25): the crates.io publish, since every crate here is `publish = false`, the SDK included; and the push of the Nix package to a public binary cache, since CtrlAssist has no cache. Both are a job each to add back. Also for review: `release-plz.yml` opens a release pull request on every push to `main`, which TisVlay's own notes say it keeps switched off because such a pull request doesn't trigger CI; it is brought over as written and can be disabled in the repository's settings. `release-plz.yml` stays as copied. *Reviewed and kept by the maintainer.*
- **What the user guide is and says** (build step 26). An mdBook under `docs/book`: introduction, installation, quick start, the tray, profiles, the command line with its generated reference, troubleshooting, how it works, requirements, and security and supply chain. It is written for someone who has never seen the project and says "controller" where the code says "pad", with a table of the words at the front. It describes installing from release packages that don't exist until the first release, and says plainly that only NixOS with KDE has been used for real. It is not published anywhere yet: TisVlay's is on Read the Docs, which needs an account and the repository move. No diagrams, so TisVlay's mermaid tooling isn't brought.
- **What a live `update` is** (after packaging). Live when the profile as kept has the setup's virtual pads: as many, of the same identities in the same order. Everything else is taken as the setup runs, the pads included, which the maintainer asked for on 2026-11-21: a pad the new profile has a use for stays open (under its source's name, under another name, or as a pad another source could mean), a new one is hidden and opened, and one given up is handed back and shown again before the update is answered. A node that selects carries on from the node of its name, by the name of what it had selected. An update of an unchanged profile is a live swap for an identical graph, not refused as nothing to do. While a setup takes a change, a `select` or an `identify` of its pads is refused as busy. In the tray, every pick but another identity is applied to a running `quick` at once, on the identity it runs with; with nothing waiting, the entry reads "Running as `quick`" and is greyed out, and with another identity picked it reads "Restart as `quick`". Changed by the maintainer the same day: another identity picked while `quick` runs restarts it at once, with no entry to click; the profile's own Start, for `quick`, writes what is picked first; and the tray logs each action it takes up. "Restart as `quick`" is left only for picks that didn't get applied.
- **The virtual DualSense** (build step 20, as built so far). Made through uhid from a copied descriptor and firmware report; its pairing report carries an address of its own, which starts `02:ca:55:` and is how the daemon knows its own pads of this kind, and its calibration is synthesized. It presents the gamepad's controls with the touchpad untouched, the sensors at rest and the battery full. Rumble is read from output reports in both of the driver's layouts. The copy is made by itself the first time a DualSense connects over USB with the hiding service there, and kept in the state directory; nothing asks the user, and nothing tells them beyond the identity turning available and a line in the log. Alternatives: a command that makes the copy when asked, or a notification from the tray when it happens. Without the hiding service nothing is copied, though on a machine with Steam's udev rules the user could open the raw node themselves; that keeps one way in, at the cost of the identity for someone with no service. `ctrlassist identities` and the tray list `dualsense` first, by name order, and as unavailable until a pad is copied. The packages now load the kernel's PlayStation driver at boot. The tests make one from a descriptor of the test crate's own, which the kernel's driver binds; what SDL and Steam make of a pad made from that, or from a real pad's data, is a hardware check.  Changed by the maintainer on 2026-11-21: the descriptor now ships, read from their own retail pad, with the firmware report synthesized, and a copied pad's data is used in its place when there is one. That reverses the decision "copied from a connected pad, never shipped" above; the repository and the binaries now carry Sony's report descriptor, which `NOTICE` says, with the trademark line. Whether that is something the project may distribute is the maintainer's judgment, not one made here. A DualShock 4 identity was offered and declined for now; it is in `docs/ideas`. Lights and trigger effects pass through to a real DualSense on USB that the hiding service has hidden, by a `raw of` request for a hidden pad's raw node (root code for the maintainer to read: `hidden_raw_node` in `pad.rs` and the `Request::RawOf` arm). Such a pad's rumble is then written to its raw node too, not asked of the kernel, which departs from the architecture's first wording for a reason found on the maintainer's pad: a report without the rumble mark ends the rumble. Not done: a reset of the lights for a pad that stops being a target, a DualSense over Bluetooth, and passing through without the hiding service. A virtual pad's address now also depends on where its daemon keeps its state, after two test daemons with a setup of one name gave their pads the same address and the kernel refused the second; a setup's address therefore changed once, which Steam sees as another controller. Tried on the maintainer's pads on 2026-11-21, with a report written into the virtual pad's raw node as a game writes one: the real DualSense's lightbar went red, green and blue as sent, and three rumble pulses reached both the DualSense, through its raw node, and the DualShock 4 beside it, through the kernel, and stopped. The DualShock 4's lightbar stayed as it was, which is the design: between unlike pads only rumble passes. Still untried: adaptive trigger effects, and any of it from a real game. The maintainer then asked for the lightbar's color to reach a DualShock 4 too: it is written to that pad's raw node, which the `raw of` request already hands over for the PlayStation driver, so no more root code was needed, where the LED files in sysfs would have needed some. A DualShock 4's rumble goes the same way from then on. Its reports are checked only by unit tests of their bytes against the kernel driver's layout; there is no fake DualShock 4. Tried by the maintainer in a game through Steam the same evening: the DualSense's and the DualShock 4's lightbars changed color together. Rumble from Steam is the open question; a tap on the input thread, logged at debug level, was added to see what a game asks of a virtual pad.
- **Rumble from Steam, as watched through the tap** (2026-11-21, on the maintainer's machine). With the `xbox` identity, Steam's rumble test goes through the kernel's force feedback as the maintainer remembered of it: one effect, number 0, uploaded again with new strengths for every request and then played, with zero strengths to stop. The router took each upload as the level changing and both real pads rumbled. With the `dualsense` identity, Steam reads the pad through its raw node and its rumble test moved nothing: in one run two reports arrived marked as rumble with both motor bytes at zero, in the next none arrived at the presses at all, and the maintainer found the same test moves neither real pad with CtrlAssist out of the way. So nothing here points at CtrlAssist, and what Steam's test does for a DualSense isn't understood. A game's rumble through a virtual DualSense is untried; a rumble report written into it by hand reaches both pads. A later run with the whole report logged: each press of Steam's one rumble button sends a virtual DualSense a report that marks rumble in both places (`03` in the first marks byte, `04` in the later one) with both motor bytes zero and nothing else set, so it asks for rumble at no strength. A game played through Steam sent trigger effects (marks `0c`, effect type `05` for both triggers) and lights, and one report marking rumble, again at zero. So what was passed through was right, and no rumble strength ever arrived to pass on. A guess, not checked: games that know the DualSense drive its actuators as sound, over the pad's USB audio device, which a virtual pad made through uhid doesn't have. The maintainer means to try Steam's test on the real DualSense alone after a reboot, which decides whether Steam's test works at all on this machine. Settled for CtrlAssist by the maintainer after a reboot, with CtrlAssist not running and only the DualSense connected, on USB: Steam's rumble button doesn't rumble it, and neither does Hades II, which drives its lights natively. So the missing rumble is the host's, Steam's or the game's on Linux, and a virtual DualSense behaves there as the real one does. The pad and the host can do it: a rumble report written to the real pad's raw node buzzed it earlier the same day, and three 120 Hz pulses played to the rear two channels of the pad's own USB audio device, which are its actuators, were felt, softly, with that device's volume at 0.40. While Hades II ran, its sound went to the television alone; nothing was linked to the pad's audio device. Later the same evening Hades II did rumble the bare DualSense, and a capture of the pad's USB traffic shows how: Wine holds the pad's raw node and writes output reports whose first marks byte is `02` (the haptics switched to rumble, without the older rumble mark) with a strength in one motor byte (`2b` weak, `4c` strong), each followed some 100 to 300 ms later by a report with no marks, which ends it. The capture keeps only the first 32 bytes of a report, so whether the later marks byte carries the newer rumble mark, as the virtual pad needs to read these as rumble, isn't seen in it. Between rumbles the game repeats a report of trigger effects twice a second. Through the virtual DualSense the same game, restarted, sends trigger effects and lights and never a rumble strength, though Wine opens the virtual pad's raw node as it does the real one's, and the only feature reports anything asks of it (pairing, firmware, calibration, and one set of report 8) are all answered. Two guesses were tried and neither changed that: making the input report say what a real pad's does (on a USB cable, gravity on one axis, a sensor clock that moves), which is kept as the more faithful report, and reporting 250 times a second as a real pad does, which was taken out again since it costs the input thread its idle sleep. What is established: SDL run natively (`sdl2-jstest --rumble`) rumbles both real pads through the virtual DualSense, with and without the constant reporting, by a report marked the newer way at full strength. So a program reading the pad through SDL on Linux gets rumble, and what Hades II under Proton goes by is not known. Found in the end, by reproducing it outside Steam: a probe of a few lines of C against the game's own `SDL2.dll` (2.32.6), cross-compiled with nixpkgs' MinGW and run under the game's Proton, saw the real DualSense as a pad it could rumble and saw no pad at all when only the virtual one was there, though Wine built the device. SDL reads one report as it opens a DualSense, waiting 16 ms; a pad that says nothing is taken for one on Bluetooth in its limited mode, and one that goes on saying nothing is dropped. A real pad reports 250 times a second; the virtual one reported only on change. With it reporting at the real rate the probe saw it, rumbled it, and both real pads were told; and the maintainer, after restarting Hades II, felt the game's rumble through it. The earlier try of the same change was judged on a game left running, which had already dropped the pad.
- **A client never found a daemon with more than 256 things under one key alive** (found and fixed 2026-11-21). The maintainer's dev daemon had 447 remembered pads, all but five of them test pads taken in by a daemon built before fake pads were marked, and its tray showed "the daemon isn't running" for as long as it ran. The SDK took each subscription's samples from zenoh's own queue, which holds 256 and stops the session's reader when full; a subscription's history arrives while it is still being declared, before anything can read it, so the declaration never finished. The SDK now queues what a subscription delivers without bound, which the daemon's state bounds. The code was TisVlay's, copied whole: the same would happen there with more than 256 keys under one subscription, and the fix is worth carrying back. A first fix, reading each subscription as soon as it was declared, didn't help, which is how the declaration itself was found to be where it stopped.
- **The Steam blacklist fallback** (build step 21). Where a setup's pads are only grabbed, their models are added to `controller_blacklist` in Steam's `config.vdf` for as long as the setup runs, as the architecture has it. Choices made on the way: the file is edited as text, one line, as 0.4.0 did, with no VDF parser; an entry the user already had is never taken out, even if a setup also wanted it; a model one of the setup's own virtual pads presents is left out, so a real DualSense stays visible to Steam beside a virtual DualSense when there is no hiding service; the list isn't updated when a live update swaps pads; nothing tells the user that Steam needs restarting beyond the daemon's log and the guide; and a daemon started to take the tests' pads leaves Steam's files alone. Not tried: against a running Steam, which may write its own copy of the file back as it exits. The maintainer's own `config.vdf` was read for its shape and not written to.
- **A virtual DualSense wakes the input thread 250 times a second** (2026-11-21). It reports all the time because the pad it passes as does and SDL drops one that doesn't; see the architecture. That gives up "never wakes while idle" for as long as such a pad exists, and only then. It is the pad's own rate and not a timeout of ours, but it is a period the daemon keeps, so it is here to be looked at. Alternatives: a slower rate, which SDL's 16 ms wait would bear down to about 100 a second, at the price of being less like the pad; or reporting only while something has the pad's raw node open, which the kernel doesn't tell a uhid device apart from its own driver having it open. Not measured: what it costs in power on a handheld. Since then an agent read SDL 2.32.6, the game's DLL and Proton's Wine for what is needed (its report is not checked by experiment yet): SDL2 reads once for 16 ms as it opens the pad, and a pad silent then is taken for Bluetooth in simple mode, dropped after 500 ms, kept claimed so no other backend shows it, and given no rumble; one 64-byte report inside that read is enough for good, but nothing tells a uhid pad that a game is opening it under Wine, so only a steady stream with gaps under 16 ms is safe. That puts the floor near 100 to 125 reports a second rather than 250. SDL3 doesn't have the problem, and the "native SDL2" that was content was SDL3 through `sdl2-compat`. It also notes SDL3 may rumble a pad whose firmware it never read by the newer marking only, which the emulator already takes. To confirm before lowering the rate: probe runs at 33, 20, 12 and 8 ms periods, expecting a sharp edge near 16. A second read by the same agent, for ways to do less (again not checked by experiment here, but for what it marks as tested): opening a raw node raises an inotify event for any file type, after the new reader's queue exists, so a report written on that event reaches it; the kernel's own open event to a uhid pad fires once, when the driver binds, and never for a game; `/proc` shows who holds the node (Steam once and the game's `winedevice.exe` twice, as it looked). Under Wine the game's own open never leaves Wine, so there a stream is needed for as long as a Wine process holds the node, at a gap under 16 ms. Having the kernel repeat the report (HID-BPF, a USB gadget) saves only the daemon's own wakeup, the cheapest part: each report also wakes every reader of the raw node, and of the pad's motion sensor node whatever its bytes say. Other emulators all stream without pause: InputPlumber at 250 a second, inputtino (Sunshine, Wolf) at 100, ViGEm at 200, Handheld Daemon at 25 when idle. What it would build: watch the node with inotify; write one report on every open; stream at 10 ms, each beat counted from the last report written so real input replaces beats, only while a Wine process or one that can't be identified holds the node. No timeout in it, but a scan of `/proc` and a rule about process names. The maintainer has not chosen.
- **Fake pads and a daemon in use** (2026-11-21). The maintainer's dev daemon had run beside the suite and remembered ninety test pads. Every fake pad now carries a marker and a daemon ignores marked pads unless started with `--test-pads` (hidden) or `CTRLASSIST_TEST_PADS`, so an installed daemon is guarded as well as the dev one, which is what the maintainer asked about. The marker is no part of what a pad is known by. The fake pads keep vendor `1209`, which is pid.codes' for open hardware and so no marker by itself; their products aren't registered to anyone, and moving them into the range pid.codes sets aside for testing (`0001` to `0010`) was offered and not asked for. Steam still adopts every fake pad while the suite runs.
- **Who the hiding service serves, and when it looks** (2026-11-21). It decided once, as a client connected, whether that client was the user in front of the machine. The daemon connects as it starts, with the user's services, and the daemon's virtual machine check once caught that being before the session was in front: every hide was then refused for the life of the connection, and the setup's pads were grabbed. It now looks again at each request from a client not yet found in front, and one found in front stays so. Root code for the maintainer to read: the `permitted` lines in `crates/ctrlassist-hider/src/main.rs`. The cause is read from the virtual machine's log (the session was a `tty` one when the daemon connected, and both hides were refused), not from the refusal itself, which the log doesn't carry.
- **A test that failed once in about seventy runs, and what was done** (build step 20). `with_the_hiding_service_a_setup_s_pads_are_hidden_reopened_and_restored` once saw the reconnected pad hidden afresh where it expects a reopen. It was not reproduced in sixty further runs, so the cause is a reading of the code, not an observation: the daemon can hear from the input thread that a pad went and find a pad on its node again before udev has told anyone the pad is back; the service then says it is absent and the daemon hides it afresh and gives up the old name, which its code is written to do. The test now accepts either, and prints everything that was asked if neither. The stand-in service's retried pad listing is gone: three thousand listings under four threads making and dropping pads never failed or missed one, so it was answering nothing.
- **What the tray's notifications are decided from** (build steps 18 and 19). "Pads only grabbed" is said when a setup starts under a daemon whose mechanism is grab. A pad that the hiding service is there for but refuses, which the daemon then grabs, is not said: telling that from a pad whose hidden flag simply hasn't arrived yet needs the setup's state to carry it, which it doesn't. "No rumble" is said for any pad in a starting setup that can't rumble, whether or not the profile sends rumble to it.
- **Quick start and a profile that starts by itself** (build step 18): with "start by itself" ticked, the daemon starts `quick` at the put if both pads are there, and the tray takes that as its start having worked.
- **The tray's icons** are theme names (`input-gaming`, and the dialog warning and error icons when a setup is held or failed), with no icon set of the project's own yet.
- **Two of the tray's files are out of the coverage figure** (build step 18): `desktop.rs`, which puts the tray item and the notifications on the session bus, and `service.rs`, its entry from the command. Neither can run without a desktop, as the hiding service's root files can't without root, which the maintainer agreed to exclude. Everything they call is tested: the menu from fixtures, the notifications from pairs of snapshots, and the whole loop against a live daemon with the tray's state held by the test. Their check is the maintainer's look on KDE.
- **When a profile starts by itself** (build step 16). A profile with `auto-start` is started by the daemon only when it would run, not be held: at daemon start, when it is put, and when a pad it names connects. Stopped by hand it stays stopped, and other pads arriving don't restart it; plugging one of its own pads in again does. Alternative: restart it whenever it isn't running, which makes it impossible to stop without editing the profile. *Reviewed and kept by the maintainer, 2026-11-21.* Found on the maintainer's pads on 2026-11-21 and fixed: with the hiding service, stopping such a setup by hand started it again at once, because showing its pads again re-binds their drivers and each pad then goes and comes back; that arrival now prompts nothing. A pad with no driver to re-bind never goes, so its next real arrival is taken for that one and prompts nothing either, once.
- **What `select` takes** (build step 16): the node by its name in the profile, and a choice by name (a mux's inputs as the profile names them, a demux's outputs by number), by place, or none for "the next". `ctrlassist setups` shows the choices with the selected one in brackets. A mux that follows a switch won't hand over to a pad that isn't connected; that is the core's rule, and `select` then changes nothing. In a preset the node is called `mux` or `demux`.

## Deviations

- **The first release waits for the GUI** (2026-11-21). "Decided" has the first release as daemon, CLI and tray, with the GUI a later minor release. The maintainer chose to build the GUI now on this branch and ship 0.5.0 with it; the TUI still follows. Its decisions and steps are in [the GUI plan](gui.md), which also brings in the icons crate and the tray's notification switches that the entry below left out.

- **The hiding service passes no hidraw descriptor yet** (build step 6). The architecture has it open a hidraw node for an allowlisted driver. Nothing reads one until the DualSense identity (build step 20), and the path can't be exercised in the virtual machine without Sony's report descriptor, so it lands with that step. The rule denies hidraw nodes now. Landed at the start of build step 20 as a `raw` request: the pad is named by a descriptor on its event node, as for hiding, the driver must be `playstation`, and the hidraw node comes back open with nothing hidden or remembered. It is root code for the maintainer to read (`crates/ctrlassist-hider/src/pad.rs`, `raw_node`, and the `Request::Raw` arm in `main.rs`). The virtual machine check covers its refusals; the grant itself is checked once there is a pad the PlayStation driver binds to in the virtual machine, which is the virtual DualSense.
- **The Steam-driving dislodge recipe went with `spikes/hiding`** (build step 6). It ran the spike's probe. Its replacements, `just hider-dev` and `just hide-pad`, go through the real service; starting Steam and reading what it lists is by hand.
- **`ctrlassist-hider` depends on `libc`** as well as `rustix` and `udev` (build step 6): the login library is C, and its strings are freed with `free`.
- **CI opens uinput on its runner** (build step 7), so the pad reader's tests run there and count toward coverage; without that the floor would fail in CI. Like the rest of the workflow, this first runs after the repository move, along with the system libraries the workflow now installs.
- **The `evdev` crate is vendored with a fix** (build step 8). Its call that sets a virtual pad's `phys` was always refused by the kernel (it declared the wrong request size), which the own-output marker needs. At the maintainer's direction the crate is carried under `vendor/` with the one-line fix, to soak here before any upstream PR; a first workaround that tracked virtual pads by device number was replaced by it.
- **The generic identity reports 0.4.0's numbers** (build step 8), USB 1234:5678, because those are what SDL and Steam were seen to adopt. They are the `evdev` crate's sample numbers, not ours; numbers of our own are a question for the release.
- **No CPU-time limit on the input thread** (build step 9). The architecture asked for one beside real-time scheduling. Exceeding `RLIMIT_RTTIME` kills the process, which would take every virtual pad with it; the kernel's own limit on real-time threads already protects the machine.
- **The queues are the standard library's bounded channels,** not a lock-free queue crate (build step 9): they are only ever polled from the input thread, never block it, and add no dependency.
- **The bench no longer times 0.4.0** (build step 9). It runs the input thread in its own process; the comparison is in the architecture. `spikes/zenoh` stays until its step, but its bench recipe went with `spikes/loop`, whose binary it drove.
- **Panic isolation is untested** (build step 9): nothing in a setup's handling can be made to panic from outside, which is the point, so the guard is exercised only by reading it.
- **Build step 13 lands in three commits:** the protocol half (session configuration, wire errors, the rpc table, the version check, and its wire test); the daemon and the CLI with `service daemon` and `status`, which, as in TisVlay, need only the protocol crate; then the SDK crate with its client and watcher, which the first command that reads state needs.
- **The daemon listens as a zenoh peer, not a router** (build step 13), as TisVlay's daemon does. A router is needed only where clients must reach each other through the hub, which CtrlAssist's never do.
- **Streaming rpcs and parked replies were trimmed** from what was copied out of TisVlay's protocol crate (build step 13): no CtrlAssist rpc streams, and nothing yet answers later through its own correlation. They return, from TisVlay, with the first rpc that needs them.
- **The SDK is TisVlay's with one service instead of three** (build step 13): no `Service` type, no site, and one mirror, which so far holds only the daemon's own state. Its errors are written by hand, as this workspace's other typed errors are, where TisVlay derives them with `thiserror`. `DaemonClient::check_release` is added, since no rpc beyond `info` exists yet to pass through the gate. TisVlay's cut-link conformance suite is not ported: it needs the socket relay from TisVlay's test crate, which arrives with the first test that needs a link cut under a running daemon (a Bluetooth drop is a pad's, not this link's). `status` does not use the SDK, as in TisVlay; the first command that does is `pads`.
- **A one-shot command hands the SDK its own session** (build step 15). `DaemonClient::connect` keeps dialing, as a tray needs, so with no daemon a command waited two seconds to say so. The CLI now opens a session that fails at once and passes it to `DaemonClient::with_session`, which TisVlay's SDK also has.
- **Build step 16 lands in several commits,** as build step 13 did: setups without hiding first, since everything else in the step hangs on a setup existing; then hiding; then `select` and auto-start; then the VM check, the bench and the spike's removal; then `update` and `identify` for a pad in a setup, which are moved behind the VM check because proving the daemon against the real hiding service matters more than either. The marked stop is after the last.
- **`update` always restarts** (build step 16), where the architecture has it live when the virtual pads are untouched. The maintainer chose this on 2026-11-21: the live change is new code on the real-time path and waits for hardware QA. The rpc already carries the answer, `disruptive`, and a dry run, so adding the live path changes no client. Decided 2026-11-21, after the maintainer tried the stack on real pads: the live change is built after packaging, and once it exists the tray's quick start applies a pick at once where that can be done live, with only disruptive picks (pads, identity) waiting for a click. Built 2026-11-21: an update is live when the profile has the setup's virtual pads, whatever its pads, and the tray applies such picks at once.
- **The tray leaves out TisVlay's notification switches and its icons crate** (build steps 18 and 19). TisVlay's tray serves per-category notification switches to its GUI over a settings service of its own, and resolves icon names against the desktop's theme through a crate of its own. CtrlAssist has no GUI yet to show switches in, so all four notifications are always on, and it names stock theme icons directly. Both can come from TisVlay when the GUI does.
- **Build steps 18 and 19 landed as one commit,** since the notifications are read off the same snapshots the menu is made from. The tray takes its logging from the daemon crate, where TisVlay has a runtime crate for what its services share; that crate arrives when a third thing needs it.
- **`notify-rust` is held at 4.18,** TisVlay's locked release: 4.19 moved to zbus 6 while ksni is on zbus 5, and the one-version gate refuses two.
- **Build step 23's "container install test" is `just package-test`,** run by hand with docker, not yet a CI job: the release workflows are build step 25. TisVlay's supply-chain recipes around the packages (SBOMs and their check) come with that step too.
- **The license bundle uses nixpkgs' cargo-about as it comes** (build step 24), where TisVlay pins one release: its pin exists for the Slint crates' license files, and CtrlAssist has none.
- **TisVlay's funding file isn't brought** (build step 27): whether and how the project takes sponsorship is the maintainer's to set up. The issue forms point questions at GitHub Discussions, which has to be switched on for the repository.
- **The gate run that reported 15 of 16 hooks once** (noted for QA on 2026-11-21) is explained: a device test took a virtual pad's node path no longer existing as the pad being gone, and the kernel hands a freed node number to the next pad made, which with tests running side by side can be another test's. It failed about one run in thirty. The test, and the newer ones like it, now know a virtual pad by its own `phys` mark; thirty runs of the whole suite then passed. One later gate run again counted 15 without its output being kept; forty runs of the suite and four of the gates after it were clean, so a rarer failure may remain. nextest runs without retries, as in TisVlay, so it will show when it recurs. That rarer failure was then caught, and it was the daemon's, not a test's: a setup whose pad had left opened the node the pad was last seen on, and where another pad had been given that node in the meantime, took the other pad. The daemon now checks that what it opened is the pad it wanted, and a test drives the race.
