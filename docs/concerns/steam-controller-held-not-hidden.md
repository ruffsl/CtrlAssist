# A Steam Controller in a setup is held, not hidden, and Steam still reads it

A setup reads a Steam Controller (2026) pad through its raw node, which has the kernel's driver take the pad's gamepad and motion devices away for as long as it is open. Games that read event nodes, and SDL's other drivers, see nothing of the pad then, as of a pad grabbed. Two kinds of reader see it all the same, through the same raw node, beside the setup's virtual pad: Steam, which opens the raw node of every Valve pad itself, and any game whose SDL3 reads the pad with its own driver for it (`SDL_hidapi_steam_triton.c`), which it does by default. To them the pad is not hidden at all, and a press arrives twice.

The hiding service doesn't take the pad. It refuses any pad whose HID device could type or point, which would be cut off with it by the re-bind that hiding is, and this pad's one HID device carries its lizard mode's keyboard and mouse beside its gamepad (the published retail descriptor, and the spike's fake built on it). Its rule couldn't name the pad's raw node either: it is a second HID device's, the client device the driver makes, which no marker the service writes names. Making an exception loosens a rule the service's safety rests on, which is the maintainer's to decide.

**What is known.** The driver taking the pad's input devices away while the raw node is open, and that the mouse and keyboard stay, were seen in a virtual machine on Linux 7.3.4 against a uhid stand-in. That Steam opens the raw node, and that SDL3 reads it by default, is read in their sources and rules, not seen with this pad. Whether Steam honors its controller blacklist for its own pad, which the daemon writes for a profile that asks for Hidden as for any pad only grabbed, is not known. What the grant of the raw node to the seat allows, and the race with another program's hold, are [their own concern](steam-raw-node-grant.md).

**Risk.** High for anyone who plays through Steam: a Steam game sees the real pad beside the virtual one, and the assist's help comes with the primary's every press twice. Low for games started outside Steam that read pads the usual way.

**Mitigation.** The window and the tray show the pad as Grabbed, not Hidden, and a profile that asks for it to be left visible is refused. The user guide says what is seen and what can be done, which today is little.

**Closes when** the maintainer decides how the pad is to be hidden, if at all, and that is seen to hold against Steam and an SDL3 game. Before that, with a pad: run a profile of it with Steam running and look in Steam's controller settings for one pad or two; run an SDL3 program that lists controllers (`testcontroller` from SDL3's tests) and count them; and with the profile at Hidden, restart Steam, and see whether the blacklist entry the daemon wrote keeps Steam from listing the real pad.
