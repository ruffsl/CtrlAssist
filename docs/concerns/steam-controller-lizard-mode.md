# A Steam Controller is taken out of lizard mode as the kernel's driver takes it, untried on the pad

With no program holding it, a Steam Controller (2026) types and points: its buttons and trackpads drive a keyboard and a mouse that are part of its own HID device, which the pad calls lizard mode. While a setup holds the pad's raw node, the kernel's driver sends the pad nothing, so turning lizard mode off is the daemon's: the pad's writer thread, once as it starts, clears the pad's keys and pointer, then turns lizard mode and the pad's own watchdog off and asks the motion sensors for their raw readings, as the kernel's driver does for the pad when nothing holds its raw node ([the input thread](../architecture.md#the-input-thread)). With the watchdog off the pad stays so, and nothing is sent again. Closing the node, however the daemon ends, has the driver set the pad up as it was.

SDL does otherwise: it leaves the watchdog on and sends lizard mode off every three seconds. That was built first and given up for the kernel's way, the maintainer's choice on 2026-11-26: a feature report holds the kernel's lock over all raw nodes (`minors_rwsem`) for as long as it waits on the pad, up to five seconds on uhid and the USB core's own limit on a cable, with every raw node's opening, closing, coming and going waiting behind it, and one sent every three seconds to a pad slow or silent would hold it most of the time.

**What only the pad can say:**

- **Whether the pad stops typing and pointing.** The requests are the kernel's own for this pad, so this is expected; nothing here has seen it.
- **Whether a pad behind a Puck or over Bluetooth fails a feature report with `EPIPE`,** as the kernel's driver says "the wireless controller" does, trying it again up to 50 times 20 ms apart. The writer makes one try, and tries again only with the next rumble level the pad is sent, so such a pad would type and point until a game next rumbled it.
- **Whether a pad slow or silent to a feature report stalls every raw node on the machine,** now only as it is taken: two requests, each holding the lock while it waits. Whether a real pad can be slow so, behind a Puck out of range or over a weak Bluetooth link, is not known.
- **What another program's settings do meanwhile.** Steam turns the motion sensors off when it has no use for them, and may set lizard mode or the watchdog as its own configuration says; nothing here puts them back until the pad is taken again. A pad the hiding service has hidden is out of such a program's reach.

**Risk.** Medium for the first, which would show on every desktop as stray typing or pointer movement while playing; low for the second and third, which need a wireless link that answers badly; medium for the last where Steam runs and the pad isn't hidden.

**Mitigation.** The writer's requests are tested against the fake, which answers at once: each is made once, in the kernel's order, and a refused one again with the next level. Should a wireless pad refuse them, trying again as its next report arrives, which says the pad is there, would mend it without a clock.

**Closes when** each is seen with a pad. On a cable, with a profile of the pad running and a text editor focused, press every button and stroke both trackpads: nothing is typed and the pointer doesn't move (`libinput debug-events` shows nothing from the pad's keyboard-and-mouse device), and still nothing after a minute of play, which a watchdog left on would have shown. Stop the profile: the pad types and points again. Behind a Puck and over Bluetooth, run `strace -f -e trace=ioctl -p <daemon>` as the profile starts and look for `HIDIOCSFEATURE` failing with `EPIPE`, and for any that takes more than a moment to return; while one does, opening another raw node (`hid-recorder` on a DualSense's, say) waits with it. With Steam running and the pad not hidden, tilt the pad behind a virtual DualSense and see whether its motion stops.
