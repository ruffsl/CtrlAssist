# A Steam Controller's lizard mode is kept off as SDL keeps it, untried on the pad

With no program holding it, a Steam Controller (2026) types and points: its buttons and trackpads drive a keyboard and a mouse that are part of its own HID device, which the pad calls lizard mode. While a setup holds the pad's raw node, the kernel's driver sends the pad nothing, so keeping lizard mode off is the daemon's: the pad's writer thread sends lizard mode off, with the motion sensors asked for their raw readings, as it starts and every three seconds after, counted from when the last such request returned, as SDL does; the pad's own watchdog is left on, so that a daemon that hangs holding the node leaves the pad to type and point again ([the input thread](../architecture.md#the-input-thread)). Closing the node, however the daemon ends, has the driver set the pad up as it was.

**What only the pad can say:**

- **Whether lizard mode off alone stops the pad typing and pointing.** The kernel's driver clears the pad's mappings of its buttons to keys first (`clear_digital_mappings`); SDL doesn't, and the daemon follows SDL. If the pad still types or points with lizard mode off, a game gets a key or a pointer movement with each press, and the clear is one frame more at the writer's start (`steam::clear_digital_mappings`, written and unused).
- **How long the watchdog is.** Nothing published says. If it is under three seconds, or near it, the pad falls back to lizard mode between two of the writer's requests, and types or points for that moment.
- **Whether a pad behind a Puck or over Bluetooth fails a feature report with `EPIPE`,** as the kernel's driver says "the wireless controller" does, trying it again up to 50 times 20 ms apart. The writer makes one try and the next an interval later, so such a pad would stay in lizard mode for three seconds at a time.
- **Whether a pad slow or silent to a feature report stalls every raw node on the machine.** The request holds the kernel's lock over all hidraw nodes (`minors_rwsem`) for as long as it waits, up to five seconds on uhid and the USB core's own limit on a cable, and every raw node's opening, closing, coming and going waits for it. Counting the interval from the request's return holds it at most five seconds in every eight. Whether a real pad can be slow so, behind a Puck out of range or over a weak Bluetooth link, is not known.

**Risk.** Medium for the first two, which would show on every desktop as stray typing or pointer movement while playing; low for the last two, which need a wireless link that answers badly.

**Mitigation.** The writer's requests and their timing are tested against the fake, which answers at once. Whether to hold lizard mode off back while the pad's reports have stopped coming, which would take a silent pad's requests away altogether, is a recommendation left with the maintainer in the plan's For review.

**Closes when** each is seen with a pad. On a cable, with a profile of the pad running and a text editor focused, press every button and stroke both trackpads: nothing is typed and the pointer doesn't move (`libinput debug-events` shows nothing from the pad's keyboard-and-mouse device). For the watchdog, with the profile running, stop the daemon without closing anything (`kill -STOP` on its process) and time how long until a button types or a trackpad points again, then `kill -CONT` it: it must be well over three seconds. Behind a Puck and over Bluetooth, run `strace -f -e trace=ioctl -p <daemon>` while the profile runs and look for `HIDIOCSFEATURE` failing with `EPIPE`, and for any that takes more than a moment to return; while one does, opening another raw node (`hid-recorder` on a DualSense's, say) waits with it.
