# The seat user is given a Steam Controller pad's raw node

The daemon reads a Steam Controller (2026) pad through the raw node of the client HID device the kernel's `hid-steam` makes beside the pad's own, which a stock machine gives to root alone. The rule the packages ship, `70-ctrlassist.rules`, gives that node to the user in front of the seat, by the `uaccess` tag, for the pad's four product numbers (`28de:1302` on a cable, `1304` in a Puck, `1305` in a Steam Machine's receiver, all on USB, and `1303` over Bluetooth) and only for the client device, which the driver puts in a group of its own, `0103`.

**What the grant allows.** Any program of the seat user's can open the node, and with it:

- read everything the pad reports, and send it any output or feature report: its settings, its lizard mode, its haptics, and Valve's commands for updating its firmware among them;
- take the pad's joystick away from every other program, as opening the node does;
- **read the pad while a setup holds it.** A program that reads Steam Controller pads raw, as Steam does and as SDL3's own driver for this pad does by default in any game built on it, opens the node beside the daemon, and reads the physical pad beside the virtual one the setup makes. For such a program, holding the pad hides nothing: the game sees both. That is the gap left where the hiding service doesn't take this pad, as behind a Puck or over Bluetooth ([its own concern](steam-controller-hiding.md)), made wider by the grant where Steam's rules aren't there already.

**What other programs' holds do to the daemon.** While no setup holds the pad, a program that opens and closes its raw node takes its event node away and has the driver make it anew. The daemon hears that as the pad leaving and plugging in again: it publishes the pad gone and back, and a profile that starts by itself when the pad is plugged in may start. While the other program holds the node, the pad is published as gone. A setup that wants the pad then waits for it, and takes it once its node is back; nothing waits on a timer, and nothing is left behind once the node is back or the pad is unplugged.

**The race a hold can't close.** The daemon marks a pad's event node as going for its own hold before it opens the raw node, and hears that mark before anything its own opening causes. If another program opens the raw node first, the node's going is that program's doing and comes before the mark: the book takes it for the pad leaving and publishes it gone, though the setup goes on to open the node and read the pad. The setup runs; the pad is listed as disconnected meanwhile, and its mark falls on no node. When both have let go, the node comes back, which the book takes for the pad plugged in: it is listed again, free, and a managed profile that wants it may start once. Nothing loops, since each going and coming is a hold that someone made, and nothing is left: the pad's next node puts it right.

**Risk.** Low on one person's machine, where Steam's own rules give the seat every raw node of Valve's vendor number, this one among them, wherever Steam is installed: there the grant is already made. Where several people share a machine, one user's program could keep the node open, switch away, and go on reading the next user's pad, and could send it firmware commands; logind takes the access away on a switch, but a descriptor already open stays good, as for [uinput and uhid](uinput-uhid-grant.md). The logind behavior here is as the agent that wrote the rule knew it, not as observed.

**Mitigation.** The rule matches the client device by its driver, its group and its four product numbers, so no other raw node of Valve's, a Puck's charging-pin interface say, is given.

**Closes when.** The raw node is opened for the daemon by something the system trusts, as the hiding service opens a PlayStation pad's, and the seat is given nothing. That waits on the hiding service taking a pad that has a keyboard and a mouse beside its gamepad, which is the maintainer's to decide.
