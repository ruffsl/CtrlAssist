# A user with no seat can stop the hiding service accepting on older kernels

The hiding service refuses descriptors on a connection until it has admitted it, within its caps, so a connection it won't serve carries nothing whose close could block (see [the architecture](../architecture.md#the-hiding-services-protocol)). That takes Linux 6.16, which has the socket setting (`SO_PASSRIGHTS`), and systemd 258, whose socket unit sets it (`AcceptFileDescriptors=no`) on the listener before anyone connects.

Without it, the closer is the only defense. A client can pass descriptors on a connection before it is accepted, and the connection's close releases them on whichever thread closes it; the service closes the connections it won't serve on a thread of its own, the closer, through a queue with room for 64, so that close never blocks the thread that accepts. A user with no seat gets past that with 74 connections: eight held, the most such a user may hold; a ninth that carries a TCP socket made to linger, its data never read, which the closer is held in closing for as long as the user keeps the socket's reader open; 64 more, which fill the closer's queue behind it; and one more, which the main thread keeps for want of room, accepting nothing more until the closer has room. Set up once, it holds.

- **On a kernel before 6.16,** at any time: the kernel has no such setting, and every connection may pass descriptors. The service says so as it starts ("this kernel can't refuse descriptors to a connection not yet admitted").
- **With systemd before 258 on 6.16 or later,** only before the service first starts, or after it is restarted: systemd ignores the unit's setting, and the service clears it on the listener as it starts (and says so), but a connection already queued has the listener's setting from when it connected. The service stays once started, so this is the time from boot until the seat user's daemon first looks for it, and after a package upgrade restarts it. The same holds on systemd 258 or later for a socket that has kept listening since before its unit gained the setting, until the socket is next restarted: the NixOS module restarts it when its unit changes, and the packages' install script at an upgrade with no service running; with one running, the script restarts the service alone, which clears the setting itself as it starts. The service's warning names both causes, being unable to tell them apart.

At the time of writing that includes every long-term kernel series before 6.16, 6.12 among them, on which the `hider-old-kernel` virtual machine check runs the service; and Debian 12 and Ubuntu 22.04 by their systemd, 252 and 249, which the [plan's minimum versions](../plans/hider-rootless.md#minimum-versions) name.

**Risk.** Medium on a machine with local users who aren't at a seat (another account, a service account someone has broken into), none on one person's. The service goes on serving the connections it has: pads already hidden stay hidden, reconnect and are shown again as asked. But it accepts nothing new for as long as the attacker holds the close: the seat user's daemon's next connection waits in the backlog unanswered, so a setup that starts then waits for the service, its pads neither hidden nor grabbed, until it is stopped; nothing new is hidden and no DualSense's raw node opened. Keeping the backlog full, which any local user can do on any kernel, comes close, but takes connecting without stopping and lets the seat user through between.

**Mitigation.** On Linux 6.16 and systemd 258 or later, none needed. Before them, the closer keeps a single blocking close off the main thread, and the caps keep the attacker to eight connections and all users with no seat to 32, which is what makes 74 the number.

**Closes when.** The kernel and systemd on the distributions the packages support are 6.16 and 258 or later; or the close of a connection not served is made unable to block on older kernels. Two ways were seen to work in a spike on Linux 6.18 and set aside for this one: the closer taking every queued message off the connection and closing each socket it carries with no linger; and the close left to a child process that exits holding the connection, as a socket never lingers when its process exits.
