# A Steam Controller's report is read as its sources describe it, never from the pad

The daemon reads a Steam Controller (2026) pad wholly from its raw state report (`0x42`, or `0x45` without the orientation), laid out as the kernel's `hid-steam` at 7.3 and SDL's `SDL_hidapi_steam_triton.c` read it. Every test reads it from a fake built from those sources (`ctrlassist_test::FakeSteamController`), which the kernel's own driver binds; nobody here has the pad. Where the two sources disagree, or say nothing, the code follows SDL, whose driver was written for this pad, and says so where it does it (`crates/ctrlassist-device/src/steam.rs`).

**What only the pad can say:**

- **Which way a trackpad's vertical grows.** SDL reads a larger y as higher; the kernel reports the 2026 pad's right trackpad on `ABS_HAT1Y` as it comes, which by evdev's convention for a hat is lower, though it negates the 2015 pad's. Wrong, a finger moving up the right trackpad moves down a virtual DualSense's touchpad.
- **Where a trackpad says a finger is while none is on it.** The place is read only while the report's touch bit is set; a lifted contact keeps where its finger left. If the pad puts its last place in those fields anyway, nothing changes; if the touch bit lags the place, a lift could show as a jump.
- **The triggers' range.** Both sources take 0 to 32767. A trigger that stops short of it never reads as pulled all the way; one that goes below 0 is read as 0.
- **Whether current firmware sends report `0x47`,** which SDL's main branch reads and the kernel's driver doesn't know. A report the descriptor doesn't declare never reaches the raw node (seen in the spike), and the retail descriptor published by `Nonary/libvirtualgamepad` doesn't declare it. A pad whose firmware sends only `0x47`, with a descriptor that declares it, would be refused as its raw node is given to it (no state report declared) or, with both declared, would say nothing in the reports read.
- **Whether its sensor clock repeats.** A report whose clock hasn't moved is taken for no new motion reading, as SDL takes it. A pad that sends a fresh reading under the same time would have it ignored.
- **Whether it sends motion before it is asked.** The daemon asks for the motion sensors' raw readings with every lizard-mode-off it sends, as SDL's main branch does, because Steam turns them off. A pad that sends motion only some while after being asked shows still for that while.
- **The orientation of its motion axes.** The pad state takes the report's x, z and minus y, as both sources hand them on, which makes the report's x to the right, y away from the player and z up: a pad lying flat reads 1 g on z. Wrong, a virtual DualSense turns on the wrong axis or the wrong way.
- **What a trackpad's pressure and the capacitive bits read,** which are in the pad state and shown to no game.

**Risk.** Medium: each would show plainly as a control that is wrong or missing behind a virtual pad, not as a subtle fault, but a wrong trackpad sense or motion axis would be wrong in every game.

**Mitigation.** The reader has unit tests from bytes laid out as the sources give them, and the device and daemon crates' tests play the fake through the input thread to each virtual pad identity.

**Closes when** each is seen on a pad on a cable. With the pad plugged in and nothing holding it, `sudo hid-recorder` (from `hid-tools`) on its raw node prints the descriptor and every report: the descriptor says whether `0x47` is declared, the reports' first byte says which is sent, and the bytes after the sequence say whether motion is there before anything asks and whether the sensor clock repeats. Then run a profile of the pad alone behind a virtual DualSense (`mode = "multicast"`, `outputs = 1`, `identity = "dualsense"`) and read the virtual pad with `evtest`: a finger at the right trackpad's top left reads near 0 on the touchpad node's position axes, at its bottom right near 1919 and 1079; a trigger pulled home reads 255 on `ABS_Z` or `ABS_RZ`; and on the motion node, the pad lying flat reads gravity on `ABS_Y` and turning it flat to the left moves `ABS_RY`, as a DualSense does. Steam's controller test, on the virtual DualSense, shows the same at a glance.
