# Testing

How the workspace is tested and where a new test goes. The approach is TisVlay's: tests are hermetic, the operating system's side is faked at the seam nearest the kernel, and what can't be reached that way is checked on hardware and said so.

## Layers

| Layer | Tests | Runs in |
|---|---|---|
| Routing and feedback | Scenarios and property tests in `ctrlassist-core`: pad states in, changes and rumble levels out, no devices | `just test`, everywhere |
| Device code | Against fake pads from `ctrlassist-test` | `just test` where uinput and uhid are writable; the virtual machine check otherwise |
| The daemon | Against a live daemon on a temporary socket, with fake pads and a stand-in for the hiding service; then the built command against the real service | `just test`; `just vm daemon` |
| The platform | What a clean machine gives a seat user | `just vm platform` |
| The settings window | Its element tree against synthetic models, driven by keys, through Slint's testing backend; then the window as packaged | `just test`; `just vm gui` |
| Hardware | What none of the above can reach | By hand, listed in the change that needs it |

## Rules

- **nextest is the runner,** with one integration-test binary per crate (`tests/it/main.rs` and its modules), which links once instead of once per file. `ctrlassist-gui` has a single test file instead, `tests/theme_breeze.rs`, which is that binary by itself.
- **No retries.** A flaky test is quarantined with `#[ignore = "flaky: …"]` and a note of why, never retried into passing.
- **A bug fix starts with a test that reproduces it,** where one can.
- **Property tests check against a model written the obvious way,** not the implementation's arithmetic written twice, and assert that they are exercising real cases: a property that only ever sees refusals passes for the wrong reason.
- **A parser of outside input gets a never-panics property test.** A panic on the input thread takes every virtual pad with it.
- **Coverage has a floor** that only rises; see [build.md](build.md#ci).

## Fake pads

`ctrlassist-test` makes pads through the kernel's own injection interfaces, so the code under test runs against real device nodes rather than a mock of the input library:

| Fake | Made through | Has | Stands in for |
|---|---|---|---|
| `FakePad` | uinput | An event node and a js node; buttons, two sticks, two triggers, a hat | Any evdev gamepad; a pad with no HID driver |
| `RumblePad` | uinput | An event node; two buttons, a stick, and rumble motors that note what they were told; its maker can stop answering, as a hung program does | A pad a buzz or a game's rumble must reach, or one another program makes that has hung |
| `FakeHider` | a socket | The hiding service's protocol, hiding nothing: it hands back the pad's node and notes what it was asked | The hiding service, for what the daemon asks of it and when |
| `synthetic_dualsense` | nothing | A report descriptor of the test crate's own that declares the reports the kernel's PlayStation driver exchanges, by number and size, and a firmware report for either rumble layout | A connected DualSense's copied data, none of which is in the repository: the driver binds a virtual pad made from it as it does one made from the real thing |
| `FakeHidPad` | uhid | Those, plus a HID device with a driver bound, a hidraw node and an address | A PlayStation pad, any Bluetooth pad, anything whose driver is re-bound or whose hidraw node is read |
| `FakeSteamController` | uhid | Valve's numbers on a cable (`28de:1302`), Bluetooth (`1303`) or a Puck's slot (`1304`), bound by the kernel's own `hid-steam`: its gamepad, motion sensors and battery, and the raw node of the client device the driver makes beside it. A descriptor of the test crate's own that declares Valve's collection alone, every report it sends at the length it sends it (`0x47` only when asked), so it can never type or point; it answers the serial, the attributes and a Puck's wireless state and acknowledges every other command, so binding waits on no timeout; it keeps every feature report set or asked for and every output report, in order; and it sends state, battery and wireless reports built from typed values, its own reading of the layout | The Steam Controller (2026), on Linux 7.3 or later |

Every fake pad is marked as the tests': one made through uinput or uhid by where it says it is plugged (`ctrlassist/test/…`), which `hid-steam` copies to the input devices it makes for a `FakeSteamController`, and `FakeDualSense`, whose driver carries no such string to its input devices, by an address that starts `02:ca:7e:`. A daemon takes a marked pad for a pad to play with only when asked to (`--test-pads`, or `CTRLASSIST_TEST_PADS` set), which the tests' own daemons, the bench and the virtual machine checks do. So the suite can run beside a daemon in use, the dev stack's or an installed one, without filling its list of pads or starting its profiles. Other programs still see them: a running Steam adopts each one.

A clean machine opens neither interface to an ordinary user, so a test that needs one checks `can_make_pads()`, `uinput_available()` or `uhid_available()` and skips where it is missing, writing a `SKIPPED` line that says why. With `CTRLASSIST_REQUIRE_FAKE_PADS` set it fails instead; CI sets it, after opening uinput, uhid, the event nodes and the raw nodes on its runner and loading the PlayStation driver a fake DualSense is bound by. The virtual machine checks run as root and never skip.

A `FakeSteamController` needs more than uhid: a kernel whose `hid-steam` knows the 2026 Steam Controller, which Linux 7.3 was the first to. `can_make_steam_pads()` reads that from the module aliases `depmod` wrote for the running kernel (the module's own table isn't in sysfs, loaded or not), and from the kernel's release where none can be read. On an older kernel the test skips even with `CTRLASSIST_REQUIRE_FAKE_PADS` set, since CI's runner has one. Where the kernel knows the pad but `hid-steam` doesn't bind it, blacklisted say, it skips too, and fails only where fake pads are required; it fails there also when uhid can't be opened. It skips while Steam is running, which would take the fake for a pad of its own. Steam isn't the only program that does: any built on SDL3 with its driver for the Steam Controller opens the fake's raw node where Steam's udev rule lets it, which takes the fake's gamepad away in the middle of a test, and no test can tell them all apart, so close them while these tests run. A browser built on Chromium with a page that asks for pads is to be closed too, before any run that makes pads through uhid: it opens raw nodes as pads come and go together and keeps them after the pads are gone, which takes these fakes' gamepads away mid-test and, over a few runs, leaves the machine with no raw node for the next pad ([concern](concerns/browser-keeps-raw-nodes.md)). A desktop's battery applet may show the fake's battery, `steam-CATEST…`, while a test runs. Its raw node is root's on a machine without a rule like Steam's, so a test that opens it skips where it can't; the `device` virtual machine check, on a 7.3 kernel, is where the fake always runs. No test writes `hid-steam`'s `lizard_mode`, which is the machine's: one that needs the gamepad to speak holds the fake's menu button, as a player does, when the parameter is at its default. The device crate's tests of the fake read in a setup on the input thread (`steam_pad`) open its raw node as the pad's reader, and so run only where that node is the user's; what they see of the pad's writer they read from what the fake was sent. One waits the pad's own interval, three seconds, for lizard mode off to be sent again, asserting only that it wasn't sooner; none shortens an interval, which are the pad's and not the tests'. The SDK's tests of a live daemon with the fake (`ctrlassist`'s `steam`) have the daemon open its raw node, and skip likewise where that node isn't the user's; each names its fake by its own serial, so that a daemon beside it in another test takes no other's. That nothing ever said the pad had left is read from every state the daemon published of it, by a subscriber of the test's own, once a profile the test puts after them has reached that subscriber too, the daemon's samples arriving in the order they were put. A fake made with `same_pad_as` is the same pad plugged in again, and one in a Puck's slot that leaves it is a pad gone with its HID device staying.

So these tests run on a developer's machine with Linux 7.3 or later, and nowhere else: CI's runner has an older kernel, and the virtual machine checks run no cargo tests. Their raw node is the seat user's by CtrlAssist's own udev rule where it is installed, as Steam's rules also make it, and root's alone otherwise, so a test that opens it skips there. The `device` virtual machine check, on 7.3, drives the same fake through the fixture as root: the driver binds it, its raw node passes reports both ways, and the driver's events for a known state are checked under both values of `lizard_mode`. No test on a developer's machine writes `hid-steam`'s `lizard_mode`, which is the machine's; the virtual machine check does, in its own machine. With it at its default, a test that needs the gamepad to speak holds the fake's menu button, as a player does. The device crate's tests of the fake read in a setup on the input thread (`steam_pad`) open its raw node as the pad's reader, and so run only where that node is the user's; what they see of the pad's writer they read from what the fake was sent. One waits the pad's own interval, three seconds, for lizard mode off to be sent again; none shortens an interval, which are the pad's and not the tests'.

The fake's reports are built from its own reading of the layout, which a unit test in the device crate reads back field by field through the device crate's own parser, for each state report, the battery report and the wireless event.

A fake with lizard mode's mouse and keyboard beside Valve's collection, as a real Steam Controller's descriptor has them, can type and point, so it is made only in a virtual machine check: building one takes an `InVirtualMachineCheck`, which only a machine that says it is a virtual one (an x86 processor's `hypervisor` flag, `/sys/hypervisor/type`, firmware naming QEMU or KVM, or QEMU's `virt` device tree) and has the root-owned `/etc/ctrlassist-vm-check` the checks' configuration puts there can give.

`ctrlassist-fixture` is the same fakes as a command, for the virtual machine checks' scripts: it creates a pad and holds it until killed, a fake Steam Controller among them, saying what it is sent, lists pads with what the caller can open, reads and writes a raw node, counts what arrives on a node, reads a pad as the daemon does, forwards a pad to a virtual pad, makes a virtual Steam Controller as a profile's identity does, and hides a pad through the hiding service.

`ctrlassist-sdl-probe`, the test crate's other program for the checks, says what SDL3 makes of the machine's pads: each as SDL adds it, with the kind SDL takes it for and the node it reads it by, and each button it presses. SDL reads a Steam Controller and a DualSense with drivers of its own, through their raw nodes, so this is what a game built on SDL sees of a virtual one. It is built only with the crate's `sdl-probe` feature, on `sdl3-sys` and the system's SDL3 through pkg-config, which the dev shell and CI's image both have; `--all-features`, as the gates build, builds it.

## Wire tests

The control plane is tested on real links: a daemon, or a stand-in for one, listens on a temporary socket under `/tmp` (a path under the build tree can exceed the kernel's limit for a socket's name) and a client calls it. The CLI's tests run the built `ctrlassist` binary against such a daemon, and start and stop the daemon as its service verb.

## Virtual machine checks

Each `packaging/nix/test-*.nix` is a NixOS test exposed as a flake check and run with `just vm <name>`. They need KVM. A check asserts; it doesn't just print. They start from a machine with only systemd's own udev rules, because a developer's desktop has Steam's and others' rules installed and hides what a clean machine refuses.

## Hardware checks

What no virtual machine has is checked by hand on real pads, through the real service: `just hider-dev` runs the hiding service from the build tree as its own user, and `just hide-pad <node>` hides a pad through it and holds it hidden until Ctrl-C.

`just hider-dev` gives the service nothing the installed one doesn't have, so the machine needs, from this tree: the hiding rule, `72-ctrlassist-hide.rules`, in `/usr/lib/udev/rules.d/` (a package built from the tree) or `/etc/udev/rules.d/` (NixOS); and the user and group `ctrlassist-hider`. On NixOS both come from the flake's module from this tree, `services.ctrlassist.enable = true`; elsewhere, from installing a package built by `just package-all`. `getent passwd ctrlassist-hider` and `getent group ctrlassist-hider` each print a line when they are there, and `diff packaging/udev/72-ctrlassist-hide.rules /etc/udev/rules.d/72-ctrlassist-hide.rules` (or the `/usr/lib` path) prints nothing when the rule is this tree's, except, on NixOS, the store paths of `chgrp`, `chmod` and `udevadm`. A rule from another commit can name markers the tree's service doesn't write. The recipe refuses when the user, the group or the rule is missing, and while the installed service's socket or service is active: the two share the marker directory, `/run/ctrlassist/hide`, which the installed service empties as it starts and as it stops. It prints the commands that stop the installed one and start its socket again afterward; stopping it shows again whatever it had hidden. On NixOS, a `nixos-rebuild switch` while the recipe runs starts the installed socket again with `sockets.target`.

`ctrlassist-hider check <node>` prints what the service makes of a node without changing anything. `just bench` times the input path, and `just bench-motion` times it with two fake DualSenses read for motion into a virtual DualSense. `just forward-pad <node>` puts a virtual pad in front of a real one, to see what Steam and SDL make of each identity.

## GUI testing

`ctrlassist-gui-app/tests/it` makes an `AppWindow` against synthetic models and queries its element tree through `i-slint-backend-testing`'s `ElementHandle`. The tests call `init_no_event_loop()`, so many `#[test]` functions share a binary with no daemon, no wire and no event loop: they answer "does the window show the right thing for this state, and do the keys go where they should?". One test, `a_snapshot_reads_a_live_daemon_and_its_going`, starts a real daemon and input thread instead, and reads the window's state from it.

`ctrlassist-gui/tests/theme_breeze.rs` reads `ui/theme.slint` as text and checks each fixed color token against the Breeze role it is taken from ([gui/theme-breeze.md](gui/theme-breeze.md)).

### Required build setting

Slint's compiler writes element ids into the generated code only when told to at build time, and without them `find_by_element_id` and `accessible_id()` silently find nothing, so a test looks as if the window were empty. `crates/ctrlassist-gui/build.rs` turns them on for every profile but the release-derived ones, so `just build`, a bare `cargo test`, rust-analyzer and CI all have them with no environment variable, and the packages ship without. The build script's setting overrides `SLINT_EMIT_DEBUG_INFO`.

### Naming

- `accessible-label`, translated with `@tr(…)`, is what a screen reader announces; on buttons it defaults to the visible text. Tests find it with `ElementHandle::find_by_accessible_label`.
- `accessible-id`, a literal `<pane>-<element>` (`pads-row-…`, `settings-couch-mode`, `sidebar-about`), is the stable selector. The testing backend has no finder for it, so `tests/it/support.rs` has `find_by_accessible_id`, which takes the first match, and `find_all_by_accessible_id`: Slint passes accessibility properties down to descendants, so one widget answers several times, and a pane that makes a detail per row has a control of that id in each. `activate_shown` presses the one of them that is showing and enabled.

### Driving keys

The testing backend has no event loop and no key helper, but `slint::Window::dispatch_event` needs neither: a pressed and released pair runs Slint's capture and bubble handlers and its own Tab traversal at once. `tests/it/support.rs` wraps it as `press(&app, Key::Tab)`, `press_text` for typed characters, `press_shift_tab`, which holds Shift around a Tab as a keyboard or a gamepad's shoulder button does (`Key::Backtab` never arrives from a real window), and `press_with_alt`. Each ends with `settle()`, which advances the mock clock a frame and fires the timers due, so deferred focus and synthesized keys have run before the assertion; `elapse` advances further, for an animation such as a wheel scroll. A control is observed through what it does: Return on a switch fires its callback and flips `accessible_checked()`, typed text lands in a field's `accessible_value()`. Prefer effects on state the test set up itself. The key navigation itself is described in [gui/remote-navigation.md](gui/remote-navigation.md).

### Not done on purpose

- **No pixel snapshots.** Slint ships none in its testing backend, and pixel comparisons are the most flake-prone kind of test; the alternative (the software renderer, bundled fonts and a tolerance) is heavy upkeep for little signal. The user guide's screenshots are drawn that way (`just docs-screenshots`), for people to look at: they are not compared with anything.
- **No tests through Slint's MCP server.** It is for looking at the window while developing (`.claude/slint.md` has its quirks); tests use the in-process testing backend only.

### Pin

`i-slint-backend-testing` is pinned exactly to Slint's release, since its API carries no semver promise and moves helpers between modules across minor releases. A Slint bump re-pins it deliberately.

## zenoh in tests

- **A multi-threaded runtime.** zenoh refuses Tokio's current-thread scheduler, so every test that opens a session is `#[tokio::test(flavor = "multi_thread")]`.
- **No ordering across keys.** Samples on different keys may arrive in any order, so a test waits on one subscription for everything it needs rather than on several in turn.
- **History only through the advanced subscriber.** What the daemon publishes reaches a late joiner only through an `AdvancedSubscriber` with history, as the SDK's mirror uses; a plain subscriber sees only live samples, and a `get` doesn't read the cache.
- **Deadlines, not sleeps.** A wait for a sample or a state is bounded and fails with what it saw, so a hang is a failure that says why, not a stalled run.
